Behavioral pattern

Observer

Observer cho phép một đối tượng báo tin cho tất cả những ai đã đăng ký lắng nghe nó, mà không cần biết họ là ai hay sẽ làm gì với tin đó. Muốn thêm một phản ứng mới, bạn chỉ cần đăng ký thêm một listener, còn nơi phát sự kiện vẫn giữ nguyên.

Bài toán

Hãy hình dung một cửa hàng online. Mỗi khi khách đặt hàng thành công, vài bộ phận cần được biết, và mỗi bộ phận làm một việc riêng.

Khi chưa có Observer

Cách làm hay gặp là để dịch vụ đặt hàng gọi thẳng từng bộ phận ngay sau khi lưu đơn.

// Khi chưa có Observer: dịch vụ đặt hàng tự gọi từng bên cần biết về đơn hàng.
interface Order {
  code: string;
  items: number;
  total: number; // VND
}

class EmailSender {
  sendConfirmation(order: Order) {
    console.log(`  Email: gửi xác nhận đơn ${order.code}`);
  }
}

class Inventory {
  reserve(order: Order) {
    console.log(`  Kho: giữ ${order.items} sản phẩm`);
  }
}

class Loyalty {
  addPoints(order: Order) {
    console.log(`  Điểm: cộng ${Math.floor(order.total / 10_000)} điểm`);
  }
}

class OrderService {
  private readonly email: EmailSender;
  private readonly inventory: Inventory;
  private readonly loyalty: Loyalty;

  constructor(email: EmailSender, inventory: Inventory, loyalty: Loyalty) {
    this.email = email;
    this.inventory = inventory;
    this.loyalty = loyalty;
  }

  place(order: Order) {
    console.log(`Đơn ${order.code}`);
    // ... lưu đơn hàng ...
    this.email.sendConfirmation(order);
    this.inventory.reserve(order);
    this.loyalty.addPoints(order);
    // Thêm thống kê? Phải sửa hàm này, constructor và mọi chỗ tạo OrderService.
  }
}

const service = new OrderService(new EmailSender(), new Inventory(), new Loyalty());
service.place({ code: "#1001", items: 2, total: 1_250_000 });
service.place({ code: "#1002", items: 3, total: 860_000 });
  • Thêm một phản ứng là phải sửa phần lõi. Muốn ghi thống kê, bạn phải sửa place(), sửa constructor và cả mọi chỗ tạo OrderService.
  • Dịch vụ đặt hàng phụ thuộc vào quá nhiều thứ. Nó phải biết lớp email, kho, điểm thưởng và tên phương thức của từng lớp, dù việc của nó chỉ là nhận đơn.
  • Bật tắt lúc chạy rất vất vả. Tạm tắt email nghĩa là phải chèn thêm một cờ if vào giữa luồng đặt hàng.
  • Test cũng khó hơn. Chỉ muốn test riêng phần đặt hàng thôi, bạn vẫn phải dựng hoặc giả lập cả ba bộ phận.

Lời giải

Ý tưởng là tách chuyện "báo cho ai" ra khỏi chuyện đặt hàng. Đối tượng phát sự kiện, gọi là Subject, ở đây là OrderPlaced. Nó chỉ giữ một danh sách listener cùng ba phương thức subscribe, unsubscribe và notify. Mỗi bộ phận là một Observer có chung phương thức on_order_placed(order). Dịch vụ đặt hàng lưu đơn rồi gọi notify, và không cần biết có bao nhiêu listener hay chúng làm gì. Nhờ vậy, thêm thống kê hay tắt email chỉ là chuyện đăng ký ở nơi lắp ráp chương trình, không đụng tới OrderService.

observer.pypython3 observer.py
"""Observer: một sự kiện "đã đặt hàng", nhiều listener độc lập với nhau.

Chạy: python3 observer.py
"""
from dataclasses import dataclass
from typing import Protocol


@dataclass(frozen=True)
class Order:
    code: str
    items: int
    total: int  # VND


def vnd(n: int) -> str:
    return f"{n:,}".replace(",", ".")


# Observer: interface chung. Listener nào cũng chỉ cần một hàm nhận đơn hàng.
class OrderListener(Protocol):
    def on_order_placed(self, order: Order) -> None: ...


# Subject: giữ danh sách listener và phát sự kiện. Nó không biết listener nào làm gì.
class OrderPlaced:
    def __init__(self) -> None:
        self._listeners: list[OrderListener] = []

    def subscribe(self, listener: OrderListener) -> None:
        self._listeners.append(listener)

    def unsubscribe(self, listener: OrderListener) -> None:
        self._listeners.remove(listener)

    def notify(self, order: Order) -> None:
        for listener in list(self._listeners):
            listener.on_order_placed(order)


# Concrete observers: mỗi lớp lo một việc và không biết các lớp khác.
class EmailListener:
    def on_order_placed(self, order: Order) -> None:
        print(f"  Email: gửi xác nhận đơn {order.code}")


class StockListener:
    def on_order_placed(self, order: Order) -> None:
        print(f"  Kho: giữ {order.items} sản phẩm")


class PointsListener:
    POINT_VALUE = 10_000  # 1 điểm cho mỗi 10.000 ₫

    def on_order_placed(self, order: Order) -> None:
        print(f"  Điểm: cộng {order.total // self.POINT_VALUE} điểm")


class AnalyticsListener:
    def on_order_placed(self, order: Order) -> None:
        print(f"  Thống kê: ghi doanh thu {vnd(order.total)} ₫")


# Nơi phát sự kiện: lưu đơn rồi báo cho ai đang nghe, không gọi thẳng ai cả.
class OrderService:
    def __init__(self, placed: OrderPlaced) -> None:
        self._placed = placed

    def place(self, order: Order) -> None:
        print(f"Đơn {order.code} ({order.items} sản phẩm, {vnd(order.total)} ₫)")
        # ... lưu đơn hàng vào cơ sở dữ liệu ...
        self._placed.notify(order)


if __name__ == "__main__":
    placed = OrderPlaced()
    email = EmailListener()
    for listener in (email, StockListener(), PointsListener()):
        placed.subscribe(listener)
    service = OrderService(placed)

    service.place(Order("#1001", 2, 1_250_000))

    print("+ subscribe(Thống kê)")
    placed.subscribe(AnalyticsListener())
    service.place(Order("#1002", 3, 860_000))

    print("- unsubscribe(Email)")
    placed.unsubscribe(email)
    service.place(Order("#1003", 1, 2_400_000))
observer.tsnode observer.ts
// Observer: một sự kiện "đã đặt hàng", nhiều listener độc lập với nhau.
// Chạy: node observer.ts   (Node 22.18 trở lên chạy thẳng TypeScript)

interface Order {
  code: string;
  items: number;
  total: number; // VND
}

const vnd = (n: number) => n.toLocaleString("vi-VN");

// Observer: interface chung. Listener nào cũng chỉ cần một hàm nhận đơn hàng.
interface OrderListener {
  onOrderPlaced(order: Order): void;
}

// Subject: giữ danh sách listener và phát sự kiện. Nó không biết listener nào làm gì.
class OrderPlaced {
  private readonly listeners: OrderListener[] = [];

  subscribe(listener: OrderListener): void {
    this.listeners.push(listener);
  }

  unsubscribe(listener: OrderListener): void {
    const index = this.listeners.indexOf(listener);
    if (index >= 0) this.listeners.splice(index, 1);
  }

  notify(order: Order): void {
    for (const listener of [...this.listeners]) listener.onOrderPlaced(order);
  }
}

// Concrete observers: mỗi lớp lo một việc và không biết các lớp khác.
class EmailListener implements OrderListener {
  onOrderPlaced(order: Order): void {
    console.log(`  Email: gửi xác nhận đơn ${order.code}`);
  }
}

class StockListener implements OrderListener {
  onOrderPlaced(order: Order): void {
    console.log(`  Kho: giữ ${order.items} sản phẩm`);
  }
}

class PointsListener implements OrderListener {
  static readonly POINT_VALUE = 10_000; // 1 điểm cho mỗi 10.000 ₫

  onOrderPlaced(order: Order): void {
    console.log(`  Điểm: cộng ${Math.floor(order.total / PointsListener.POINT_VALUE)} điểm`);
  }
}

class AnalyticsListener implements OrderListener {
  onOrderPlaced(order: Order): void {
    console.log(`  Thống kê: ghi doanh thu ${vnd(order.total)} ₫`);
  }
}

// Nơi phát sự kiện: lưu đơn rồi báo cho ai đang nghe, không gọi thẳng ai cả.
class OrderService {
  private readonly placed: OrderPlaced;

  constructor(placed: OrderPlaced) {
    this.placed = placed;
  }

  place(order: Order): void {
    console.log(`Đơn ${order.code} (${order.items} sản phẩm, ${vnd(order.total)} ₫)`);
    // ... lưu đơn hàng vào cơ sở dữ liệu ...
    this.placed.notify(order);
  }
}

const placed = new OrderPlaced();
const email = new EmailListener();
for (const listener of [email, new StockListener(), new PointsListener()]) placed.subscribe(listener);
const service = new OrderService(placed);

service.place({ code: "#1001", items: 2, total: 1_250_000 });

console.log("+ subscribe(Thống kê)");
placed.subscribe(new AnalyticsListener());
service.place({ code: "#1002", items: 3, total: 860_000 });

console.log("- unsubscribe(Email)");
placed.unsubscribe(email);
service.place({ code: "#1003", items: 1, total: 2_400_000 });

Khi nào dùng

  • Khi một thay đổi ở một chỗ kéo theo việc ở nhiều chỗ khác, và danh sách những chỗ đó thay đổi theo thời gian, chẳng hạn có đơn hàng mới, có người dùng đăng ký, thanh toán xong hay file tải lên xong.
  • Khi bên phát không nên biết bên nghe là ai. Module lõi chỉ phát sự kiện, còn các module phụ như email, thống kê hay tích điểm tự đăng ký lắng nghe.
  • Khi cần bật tắt phản ứng lúc chạy, hoặc muốn để plugin bên ngoài gắn thêm hành vi mà không phải sửa code gốc.

Khi nào không nên

  • Khi chỉ có một bên cần biết và sẽ luôn chỉ có một bên đó. Gọi thẳng hàm đó rõ ràng hơn nhiều.
  • Khi các bước phải chạy theo thứ tự chặt chẽ, hoặc phải cùng thành công hay cùng thất bại, như trừ tiền rồi mới giao hàng. Đó là một quy trình, nên viết thành một luồng tường minh.
  • Khi sự kiện bắt đầu gọi dây chuyền nhau, listener này phát sự kiện mới và sự kiện đó lại kích hoạt listener khác. Lúc ấy luồng chạy rất khó lần theo và khó debug.

Dễ nhầm với

  • Publish/Subscribe qua message broker, như hàng đợi, Kafka hay Redis Pub/Sub, có cùng ý tưởng nhưng diễn ra giữa các service. Bên phát và bên nghe không chạy chung tiến trình, ở giữa có hàng đợi và mọi thứ chạy bất đồng bộ, trong khi Observer thường nằm gọn trong một tiến trình và gọi đồng bộ.
  • Mediator cũng giúp các bên không gọi nhau trực tiếp, nhưng trung gian biết rõ từng bên và điều phối chúng. Subject trong Observer thì không biết listener làm gì.
  • Chain of Responsibility chuyền yêu cầu qua từng mắt xích cho tới khi có một mắt xử lý xong thì dừng. Observer thì gửi tới mọi listener.
  • Event emitter, callback hay signal, như EventEmitter của Node hoặc signal của Django, chính là những bản Observer làm sẵn.

Ghi chú khi triển khai

  • Đừng dựa vào thứ tự gọi listener. Nếu kho bắt buộc phải giữ hàng trước khi gửi email, đó là một quy trình chứ không còn là hai listener độc lập.
  • Một listener bị lỗi không nên chặn các listener còn lại. Hãy bắt lỗi từng listener trong notify và ghi log, hoặc đẩy những việc chậm như gửi email vào hàng đợi.
  • Chỉ phát sự kiện sau khi đơn đã lưu thành công. Nếu phát trong lúc giao dịch cơ sở dữ liệu còn mở mà giao dịch lại bị huỷ, khách sẽ nhận email cho một đơn không hề tồn tại.
  • Nhớ huỷ đăng ký những listener không còn dùng. Chừng nào subject còn giữ tham chiếu, listener đó không được giải phóng và vẫn bị gọi như thường.
  • Hãy truyền dữ liệu sự kiện ở dạng bất biến, ví dụ @dataclass(frozen=True), để listener trước không sửa được đơn hàng mà listener sau nhận.

Kiểm tra nhanh

Sáu câu hỏi ngắn để xem bạn đã nắm Observer tới đâu. Chọn một đáp án, lời giải thích sẽ hiện ngay bên dưới.

  1. Câu 1 Mỗi khi có người đăng ký tài khoản, hệ thống cần gửi email chào mừng, tạo ví điểm thưởng và báo cho đội bán hàng. Danh sách việc này còn thay đổi thường xuyên. Cách tổ chức nào hợp nhất?

    Danh sách phản ứng thay đổi theo thời gian và phần đăng ký không cần biết ai đang nghe, nên Observer là lựa chọn hợp nhất. Gọi thẳng hay gom vào một hàm lớn đều buộc bạn sửa phần đăng ký mỗi lần thêm hoặc bớt một việc.

  2. Câu 2 Điểm thưởng được cộng 1 điểm cho mỗi 10.000 ₫. Ở bước cuối, sau khi Email đã huỷ đăng ký, đơn #1003 trị giá 2.400.000 ₫ được đặt. Những listener nào phản ứng, và Điểm cộng bao nhiêu?

    Trạm Email đã nhấc chốt khỏi thanh nên không còn nhận đơn #1003, còn ba trạm kia vẫn cắm chốt. Lấy 2.400.000 ₫ chia cho 10.000 ₫ thì được 240 điểm.

  3. Câu 3 Trong hình, bộ phận nào ứng với phương thức subscribe?

    Cắm chốt vào thanh nghĩa là đăng ký, nên từ lúc đó trạm sẽ chuyển động mỗi khi thanh bị đẩy. Nút đặt hàng ứng với lời gọi notify, còn lá cờ bật lên là phản ứng của từng listener.

  4. Câu 4 Kho bắt buộc phải giữ hàng thành công thì mới được gửi email xác nhận. Bạn nên làm thế nào?

    Observer không hứa hẹn gì về thứ tự gọi, nên dựa vào thứ tự đăng ký là một cái bẫy. Khi bước sau phụ thuộc vào kết quả của bước trước, hãy viết chúng thành một quy trình rõ ràng.

  5. Câu 5 Vì sao chỉ nên gọi notify sau khi đơn hàng đã được lưu thành công?

    Listener có thể gây ra những việc bên ngoài như gửi email, và những việc đó không rút lại được. Phát sự kiện sau khi lưu xong bảo đảm mọi phản ứng đều ứng với một đơn có thật.

  6. Câu 6 Observer và Chain of Responsibility khác nhau ở điểm nào?

    Với Observer, mọi bên đã đăng ký đều được báo và không bên nào chặn bên nào. Chain of Responsibility thì ngược lại, mỗi mắt xích có thể giữ yêu cầu lại để những mắt phía sau không bao giờ thấy nó.
