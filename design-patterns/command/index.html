Behavioral pattern

Command

Command gói một yêu cầu thành một object: lệnh biết phải làm gì, với dữ liệu nào, và cách đảo ngược chính nó. Khi lệnh đã là một object, bạn có thể xếp nó vào hàng đợi, ghi lại, chạy lại hoặc hoàn tác mà phần chạy lệnh không cần biết bên trong lệnh là gì.

Bài toán

Hệ thống kho nhận các yêu cầu điều chỉnh tồn kho của một mặt hàng: nhập thêm khi hàng về, xuất khi giao đơn. Trong một ca làm việc có ba yêu cầu:

Thứ tựYêu cầuTồn kho sau đó
1Nhập 50100 → 150
2Xuất 20150 → 130
3Xuất 15130 → 115

Sau đó người vận hành phát hiện lần xuất 15 bị nhập nhầm và cần hoàn tác nó. Hệ thống cũng cần chạy các yêu cầu lần lượt theo đúng thứ tự, ghi lại đã làm gì, và về sau đẩy chúng sang một worker chạy nền, thử lại khi lỗi.

Khi chưa có Command

Cách làm thường gặp là để handler của API sửa thẳng tồn kho ngay khi request tới:

// Khi chưa có Command: mỗi request sửa thẳng tồn kho ngay lúc nó tới.
const inventory = { stock: 100 };

// Handler của API: nhận request là làm luôn, không để lại dấu vết gì.
function handleReceive(qty: number): void {
  inventory.stock += qty;
}

function handleShip(qty: number): void {
  if (qty > inventory.stock) throw new Error("Không đủ hàng");
  inventory.stock -= qty;
}

handleReceive(50);
handleShip(20);
handleShip(15);
console.log(inventory.stock);
// Lần xuất cuối bị nhập nhầm? Không có gì ghi lại
// lần cuối là thao tác nào, với bao nhiêu hàng.
  • Không hoàn tác được. Sau khi hàm chạy xong, không còn gì cho biết thao tác cuối là gì và với bao nhiêu hàng. Muốn sửa phải tự tính rồi chỉnh tay.
  • Không có lịch sử. Muốn ghi log hay kiểm toán thì phải chèn thêm code vào từng handler.
  • Không xếp hàng hay chạy sau được. Yêu cầu được thực hiện ngay trong lúc gọi; không có gì để đưa vào hàng đợi, chuyển sang worker hay thử lại.
  • Mỗi thao tác mới là thêm một đường đi riêng. Logic chạy, kiểm tra và ghi log lặp lại ở mọi handler.

Lời giải

Mỗi thao tác trở thành một lớp Command có hai hàm execute() và undo(). Lệnh giữ sẵn mọi thứ nó cần: kho nào (Receiver) và bao nhiêu hàng. Invoker (CommandRunner) chỉ có hàng đợi và lịch sử: lấy lệnh từ hàng đợi, gọi execute(), đẩy lệnh vào lịch sử; hoàn tác là lấy lệnh trên cùng của lịch sử và gọi undo(). Client là nơi tạo lệnh và đưa vào hàng đợi.

command.pypython3 command.py
"""Command: gói mỗi thao tác kho thành một object để xếp hàng, ghi lịch sử và hoàn tác.

Chạy: python3 command.py
"""
from collections import deque
from typing import Protocol


# Receiver: kho hàng. Nó chỉ biết cộng và trừ tồn kho, không biết gì về lệnh.
class Inventory:
    def __init__(self, stock: int) -> None:
        self.stock = stock

    def add(self, qty: int) -> None:
        self.stock += qty

    def remove(self, qty: int) -> None:
        if qty > self.stock:
            raise ValueError(f"Không đủ hàng: còn {self.stock}, cần {qty}")
        self.stock -= qty


# Command: mỗi lệnh biết cách chạy và cách đảo ngược chính nó.
class Command(Protocol):
    name: str

    def execute(self) -> None: ...

    def undo(self) -> None: ...


class ReceiveStock:
    def __init__(self, inventory: Inventory, qty: int) -> None:
        self.inventory = inventory
        self.qty = qty
        self.name = f"Nhập {qty}"

    def execute(self) -> None:
        self.inventory.add(self.qty)

    def undo(self) -> None:
        self.inventory.remove(self.qty)


class ShipStock:
    def __init__(self, inventory: Inventory, qty: int) -> None:
        self.inventory = inventory
        self.qty = qty
        self.name = f"Xuất {qty}"

    def execute(self) -> None:
        self.inventory.remove(self.qty)

    def undo(self) -> None:
        self.inventory.add(self.qty)


# Invoker: chạy lệnh theo hàng đợi và giữ lịch sử. Nó không biết bên trong lệnh làm gì.
class CommandRunner:
    def __init__(self) -> None:
        self.queue: deque[Command] = deque()
        self.history: list[Command] = []

    def submit(self, command: Command) -> None:
        self.queue.append(command)

    def run_next(self) -> Command:
        command = self.queue.popleft()
        command.execute()
        self.history.append(command)  # chỉ ghi vào lịch sử khi đã chạy xong
        return command

    def undo(self) -> Command:
        command = self.history.pop()  # lệnh chạy sau cùng được hoàn tác trước
        command.undo()
        return command


if __name__ == "__main__":
    inventory = Inventory(stock=100)
    runner = CommandRunner()

    # Client: tạo lệnh và xếp vào hàng đợi. Lúc này chưa có gì chạy.
    for command in [
        ReceiveStock(inventory, 50),
        ShipStock(inventory, 20),
        ShipStock(inventory, 15),
    ]:
        runner.submit(command)
    print(f"Đang chờ {len(runner.queue)} lệnh, tồn kho {inventory.stock}")

    while runner.queue:
        before = inventory.stock
        command = runner.run_next()
        print(f"Chạy      {command.name}: {before} → {inventory.stock}")

    before = inventory.stock
    command = runner.undo()
    print(f"Hoàn tác  {command.name}: {before} → {inventory.stock}")
    print("Lịch sử:", ", ".join(c.name for c in runner.history))

// Command: gói mỗi thao tác kho thành một object để xếp hàng, ghi lịch sử và hoàn tác.
// Chạy: node command.ts   (Node 22.18 trở lên chạy thẳng TypeScript)

// Receiver: kho hàng. Nó chỉ biết cộng và trừ tồn kho, không biết gì về lệnh.
class Inventory {
  stock: number;

  constructor(stock: number) {
    this.stock = stock;
  }

  add(qty: number): void {
    this.stock += qty;
  }

  remove(qty: number): void {
    if (qty > this.stock) throw new Error(`Không đủ hàng: còn ${this.stock}, cần ${qty}`);
    this.stock -= qty;
  }
}

// Command: mỗi lệnh biết cách chạy và cách đảo ngược chính nó.
interface Command {
  readonly name: string;
  execute(): void;
  undo(): void;
}

class ReceiveStock implements Command {
  readonly name: string;
  private readonly inventory: Inventory;
  private readonly qty: number;

  constructor(inventory: Inventory, qty: number) {
    this.inventory = inventory;
    this.qty = qty;
    this.name = `Nhập ${qty}`;
  }

  execute(): void {
    this.inventory.add(this.qty);
  }

  undo(): void {
    this.inventory.remove(this.qty);
  }
}

class ShipStock implements Command {
  readonly name: string;
  private readonly inventory: Inventory;
  private readonly qty: number;

  constructor(inventory: Inventory, qty: number) {
    this.inventory = inventory;
    this.qty = qty;
    this.name = `Xuất ${qty}`;
  }

  execute(): void {
    this.inventory.remove(this.qty);
  }

  undo(): void {
    this.inventory.add(this.qty);
  }
}

// Invoker: chạy lệnh theo hàng đợi và giữ lịch sử. Nó không biết bên trong lệnh làm gì.
class CommandRunner {
  readonly queue: Command[] = [];
  readonly history: Command[] = [];

  submit(command: Command): void {
    this.queue.push(command);
  }

  runNext(): Command {
    const command = this.queue.shift()!;
    command.execute();
    this.history.push(command); // chỉ ghi vào lịch sử khi đã chạy xong
    return command;
  }

  undo(): Command {
    const command = this.history.pop()!; // lệnh chạy sau cùng được hoàn tác trước
    command.undo();
    return command;
  }
}

const inventory = new Inventory(100);
const runner = new CommandRunner();

// Client: tạo lệnh và xếp vào hàng đợi. Lúc này chưa có gì chạy.
for (const command of [
  new ReceiveStock(inventory, 50),
  new ShipStock(inventory, 20),
  new ShipStock(inventory, 15),
]) {
  runner.submit(command);
}
console.log(`Đang chờ ${runner.queue.length} lệnh, tồn kho ${inventory.stock}`);

while (runner.queue.length > 0) {
  const before = inventory.stock;
  const command = runner.runNext();
  console.log(`Chạy      ${command.name}: ${before} → ${inventory.stock}`);
}

const before = inventory.stock;
const undone = runner.undo();
console.log(`Hoàn tác  ${undone.name}: ${before} → ${inventory.stock}`);
console.log("Lịch sử:", runner.history.map((c) => c.name).join(", "));

Khi nào dùng

  • Cần hoàn tác hoặc làm lại: trình soạn thảo, thao tác hàng loạt trong trang quản trị, chỉnh sửa có nút "Undo".
  • Cần xếp hàng và chạy sau: job queue, tác vụ nền, lịch hẹn giờ. Mỗi job trong hàng đợi chính là một command được ghi lại dưới dạng tên lệnh cộng tham số.
  • Cần thử lại, ghi log hoặc kiểm toán từng thao tác một cách thống nhất, không chèn code vào từng handler.
  • Muốn tách nơi quyết định "làm gì" khỏi nơi quyết định "khi nào và chạy ra sao": nút bấm, menu, phím tắt và API cùng tạo ra một loại lệnh.

Khi nào không nên

  • Thao tác đơn giản, chạy ngay, không cần hàng đợi, lịch sử hay hoàn tác: một lời gọi hàm là đủ.
  • Thao tác không đảo ngược được (gửi email, gọi cổng thanh toán): undo() lúc đó chỉ là ảo tưởng. Hãy thiết kế một lệnh bù riêng, như hoàn tiền.
  • Số lớp lệnh tăng nhanh mà mỗi lớp chỉ bọc một dòng code: cân nhắc dùng hàm hoặc closure làm lệnh.

Dễ nhầm với

  • Strategy cũng đóng gói hành vi vào object, nhưng là để chọn cách làm một việc. Command là một yêu cầu cụ thể kèm dữ liệu của nó, có thể lưu lại, chạy sau và hoàn tác.
  • Memento hoàn tác bằng cách chụp lại trạng thái rồi khôi phục. Command hoàn tác bằng phép tính ngược (xuất 15 thì nhập lại 15). Hai cách hay đi cùng nhau khi phép ngược khó viết.
  • Chain of Responsibility chuyển một yêu cầu qua nhiều nơi xử lý; yêu cầu đó thường chính là một command.
  • Observer phát một sự kiện cho nhiều bên nghe. Command là một lệnh gửi tới đúng một nơi thực hiện.

Ghi chú khi triển khai

  • Chỉ đẩy lệnh vào lịch sử sau khi execute() chạy thành công; lệnh lỗi không được để lại dấu trong lịch sử.
  • undo() cũng có thể thất bại. Ví dụ: hoàn tác một lần nhập khi hàng đã bị xuất đi. Kiểm tra điều kiện ở đây như ở execute().
  • Trong job queue, lệnh được lưu thành dữ liệu (tên lệnh, tham số, id) rồi worker dựng lại object để chạy. Gán cho mỗi lệnh một id để lần thử lại thứ hai không trừ kho thêm lần nữa (idempotent).
  • Trong hệ thống nhiều người dùng, "hoàn tác" thường là chạy thêm một lệnh bù và ghi nó vào lịch sử, thay vì xoá lệnh cũ. Lịch sử vẫn đầy đủ để kiểm toán.
  • Giới hạn độ dài lịch sử, hoặc lưu nó ra ngoài bộ nhớ, nếu lệnh giữ nhiều dữ liệu.
