Structural pattern

Facade

Facade đặt một cửa vào đơn giản trước cả một hệ con phức tạp. Client chỉ gọi một hàm của facade, còn facade biết phải gọi những lớp nào bên trong, theo thứ tự nào và xử lý lỗi ra sao. Các lớp bên trong vẫn còn nguyên, ai cần thì vẫn gọi thẳng được.

Bài toán

Hãy hình dung một cửa hàng online. Đặt một đơn hàng ở đây thực ra là năm việc ở năm hệ con khác nhau, và phải làm đúng thứ tự:

Thứ tự này có lý do. Phải giữ hàng trước khi thu tiền, và thu được tiền rồi mới đặt lịch giao. Nếu thẻ bị từ chối, số hàng vừa giữ phải được trả lại kho. Thêm nữa, đơn hàng đến từ ba nơi là trang web, app di động và công cụ của nhân viên.

Khi chưa có Facade

Mỗi nơi đặt hàng tự gọi lần lượt năm hệ con. Ba bản chép của cùng một quy trình thì sớm muộn cũng lệch nhau, và trong ví dụ này app di động quên trả hàng về kho khi thanh toán lỗi:

  • Lỗi nằm ở chỗ rất khó thấy. Không có gì báo lỗi cả, chỉ là tồn kho cứ hụt dần, vì mỗi lần thẻ lỗi trên app lại giữ mất vài sản phẩm.
  • Client biết quá nhiều. Trang web phải biết có năm hệ con, phải gọi theo thứ tự nào và bù trừ ra sao. Muốn thêm một bước như tích điểm thì phải sửa cả ba nơi.
  • Phụ thuộc chằng chịt. Client nào cũng phụ thuộc vào năm lớp, nên chỉ cần đổi chữ ký một hàm của hệ con là đụng đến mọi client.

Lời giải

Ta gom quy trình đó vào một lớp Facade là CheckoutFacade, với phương thức place_order(cart). Facade giữ năm hệ con ở bên trong, gọi chúng theo đúng thứ tự và lo luôn phần trả hàng khi thanh toán lỗi.

Web, app hay công cụ nội bộ đều đóng vai Client. Chúng chỉ gọi một hàm, nên mọi nơi chạy chung một quy trình. Các hệ con thì không hề biết đến facade và vẫn dùng riêng được.

facade.pypython3 facade.py
"""Facade: một hàm đặt hàng che cả năm hệ con phía sau.

Chạy: python3 facade.py
"""
from dataclasses import dataclass


def vnd(n: int) -> str:
    return f"{n:,} ₫".replace(",", ".")


@dataclass(frozen=True)
class Cart:
    order_id: str
    sku: str
    qty: int
    price: int
    card: str
    email: str

    @property
    def total(self) -> int:
        return self.qty * self.price


class PaymentDeclined(Exception):
    pass


# Năm hệ con. Mỗi hệ con vẫn dùng riêng được; facade không giấu chúng đi.
class Inventory:
    def __init__(self, stock: dict[str, int]) -> None:
        self.stock = dict(stock)

    def reserve(self, sku: str, qty: int) -> None:
        before = self.stock[sku]
        self.stock[sku] -= qty
        print(f"  Kho: giữ {qty} × {sku}, tồn {before} → {self.stock[sku]}")

    def release(self, sku: str, qty: int) -> None:
        self.stock[sku] += qty
        print(f"  Kho: trả lại {qty} × {sku}, tồn {self.stock[sku]}")


class Payments:
    def __init__(self) -> None:
        self._next = 5521

    def charge(self, card: str, amount: int) -> str:
        if card.endswith("0002"):  # thẻ thử nghiệm luôn bị từ chối
            print(f"  Thanh toán: thẻ ...{card} bị từ chối")
            raise PaymentDeclined(card)
        txn = f"GD-{self._next}"
        self._next += 1
        print(f"  Thanh toán: thu {vnd(amount)}, mã {txn}")
        return txn


class Shipping:
    def book(self, order_id: str) -> str:
        print(f"  Vận chuyển: vận đơn VD-3308 cho {order_id}")
        return "VD-3308"


class Invoices:
    def issue(self, order_id: str, amount: int) -> str:
        print(f"  Hoá đơn: HD-0457, {vnd(amount)}")
        return "HD-0457"


class Notifier:
    def send(self, email: str, text: str) -> None:
        print(f"  Thông báo: gửi {email}: {text}")


@dataclass(frozen=True)
class OrderResult:
    order_id: str
    txn: str
    tracking: str
    invoice: str


# Facade: một cửa cho việc đặt hàng. Thứ tự gọi và cách xử lý lỗi nằm ở một chỗ.
class CheckoutFacade:
    def __init__(self, inventory: Inventory, payments: Payments, shipping: Shipping,
                 invoices: Invoices, notifier: Notifier) -> None:
        self._inventory = inventory
        self._payments = payments
        self._shipping = shipping
        self._invoices = invoices
        self._notifier = notifier

    def place_order(self, cart: Cart) -> OrderResult:
        self._inventory.reserve(cart.sku, cart.qty)
        try:
            txn = self._payments.charge(cart.card, cart.total)
        except PaymentDeclined:
            self._inventory.release(cart.sku, cart.qty)  # mọi client đều được trả hàng về kho
            raise
        tracking = self._shipping.book(cart.order_id)
        invoice = self._invoices.issue(cart.order_id, cart.total)
        self._notifier.send(cart.email, f"Đơn {cart.order_id} đã được đặt")
        return OrderResult(cart.order_id, txn, tracking, invoice)


if __name__ == "__main__":

    checkout = CheckoutFacade(inventory, Payments(), Shipping(), Invoices(), Notifier())

    # Client (web, app di động, công cụ admin) chỉ gọi một hàm.
    print("place_order(DH-2041)")

        print("→ DH-2042 không đặt được")

    print(f"Tồn kho SP-17: {inventory.stock['SP-17']}")

  sku: string;
  qty: number;
  price: number;
  card: string;
  email: string;

    this.stock = { ...stock };
  }

  reserve(sku: string, qty: number): void {

  }

class Payments {

  orderId: string;
  txn: string;
  tracking: string;
  invoice: string;

// Facade: một cửa cho việc đặt hàng. Thứ tự gọi và cách xử lý lỗi nằm ở một chỗ.
class CheckoutFacade {
  private inventory: Inventory;
  private payments: Payments;
  private shipping: Shipping;
  private invoices: Invoices;
  private notifier: Notifier;

  constructor(inventory: Inventory, payments: Payments, shipping: Shipping, invoices: Invoices, notifier: Notifier) {
    this.inventory = inventory;
    this.payments = payments;
    this.shipping = shipping;
    this.invoices = invoices;
    this.notifier = notifier;
  }

  placeOrder(cart: Cart): OrderResult {
    this.inventory.reserve(cart.sku, cart.qty);
    let txn: string;
    try {
      txn = this.payments.charge(cart.card, totalOf(cart));
    } catch (error) {
      this.inventory.release(cart.sku, cart.qty); // mọi client đều được trả hàng về kho
      throw error;
    }
    const tracking = this.shipping.book(cart.orderId);
    const invoice = this.invoices.issue(cart.orderId, totalOf(cart));
    this.notifier.send(cart.email, `Đơn ${cart.orderId} đã được đặt`);
    return { orderId: cart.orderId, txn, tracking, invoice };
  }
}

Khi nào dùng

  • Khi một việc nghiệp vụ cần phối hợp nhiều lớp hoặc nhiều service theo một thứ tự cố định, chẳng hạn đặt hàng, đăng ký tài khoản với các bước tạo user, gán quyền và gửi email chào, hay đóng kỳ kế toán.
  • Khi nhiều client cùng cần làm việc đó, như web, app, API cho đối tác hay job chạy đêm. Facade bảo đảm tất cả chạy chung một quy trình.
  • Khi bạn muốn bọc một thư viện hay SDK lớn thành vài hàm vừa đúng nhu cầu, ví dụ một StorageFacade chỉ có upload và signed_url đứng trước cả bộ SDK của nhà cung cấp lưu trữ.
  • Khi bạn muốn các tầng tách bạch rõ ràng, để tầng giao diện chỉ nói chuyện với một cửa duy nhất của tầng nghiệp vụ.

Khi nào không nên

  • Khi chỉ gọi một hệ con. Lúc đó facade chỉ là một lớp chuyển tiếp thừa.
  • Khi mỗi client cần phối hợp theo một cách riêng. Một facade cố gom hết sẽ đầy cờ và tham số tuỳ chọn, nên tốt hơn là tách thành nhiều facade, mỗi cái lo một việc.
  • Khi facade bắt đầu chứa luôn quy tắc nghiệp vụ của các hệ con. Đó là dấu hiệu nó đang thành một god object, trong khi facade chỉ nên điều phối, còn quy tắc thuộc về từng hệ con.

Dễ nhầm với

  • Adapter đổi interface của một lớp sang đúng interface mà client đã yêu cầu. Facade thì tạo ra một interface mới, đơn giản hơn, đứng trước nhiều lớp.
  • Mediator cũng đứng giữa nhiều lớp, nhưng các lớp đó gọi nhau thông qua mediator và biết nó tồn tại. Với Facade, lời gọi chỉ đi một chiều từ client vào facade rồi xuống hệ con, và hệ con không biết gì về facade.
  • Proxy có cùng interface với đúng một đối tượng thật và đứng thay cho nó. Facade không giả làm ai cả.
  • Service layer, hay application service trong kiến trúc nhiều tầng, thường chính là một tập facade, mỗi phương thức ứng với một use case.

Ghi chú khi triển khai

  • Hãy giữ facade thật mỏng. Facade chỉ lo thứ tự gọi, bù trừ khi lỗi và gom kết quả. Tính giá, kiểm tra tồn kho hay chính sách hoàn tiền là phần của hệ con.
  • Quyết định rõ cách bù trừ. Hãy xác định bước nào lỗi thì hoàn tác bước nào, như trả hàng hay hoàn tiền. Khi các hệ con là service riêng gọi qua mạng, đây đã là một saga nhỏ, và bạn nên ghi lại từng bước để có thể chạy lại.
  • Đừng giấu hệ con đi. Facade là lối tắt cho những việc thường làm chứ không phải bức tường, nên các trường hợp đặc biệt vẫn có thể gọi thẳng hệ con.
  • Truyền hệ con vào qua constructor. Làm như ví dụ thì khi test, bạn thay được bằng bản giả và kiểm tra được thứ tự gọi.

Kiểm tra nhanh

Sáu câu hỏi ngắn để xem bạn đã nắm Facade tới đâu. Chọn một đáp án, lời giải thích sẽ hiện ngay bên dưới.

  1. Câu 1 Trang web, app di động và API cho đối tác đều cần đăng ký tài khoản mới theo cùng các bước: tạo user, gán quyền mặc định rồi gửi email chào. Cách nào giữ cho ba nơi luôn chạy giống nhau?

    Facade gom quy trình về một chỗ, nên ba client chạy chung một đường và chỉ cần sửa một lần. Để lớp tạo user tự gọi các lớp khác thì các hệ con bị buộc chặt vào nhau, còn Adapter dùng để đổi interface chứ không để điều phối nhiều bước.

  2. Câu 2 Đơn DH-2042 đặt 3 sản phẩm SP-17 khi kho còn 10, nhưng thẻ bị từ chối. Sau khi place_order() chạy xong, tồn kho SP-17 là bao nhiêu?

    Facade giữ 3 sản phẩm nên tồn kho xuống 7, rồi khi thẻ bị từ chối nó trả lại đúng 3 sản phẩm đó và tồn kho quay về 10. Con số 7 chính là lỗi của bản chưa có facade, khi app di động quên bước trả hàng.

  3. Câu 3 Trong ví dụ, Inventory, Payments, Shipping, Invoices và Notifier đóng vai gì?

    Năm lớp đó là các hệ con làm việc thật, và chúng không hề biết đến facade. Client là trang web, app và công cụ admin, còn facade chỉ có một là CheckoutFacade.

  4. Câu 4 Dấu hiệu nào cho thấy một facade đang bị dùng sai?

    Facade chỉ nên điều phối thứ tự gọi và bù trừ khi lỗi, còn quy tắc nghiệp vụ thuộc về từng hệ con. Khi facade ôm luôn các quy tắc đó, nó đang dần thành một god object vừa khó sửa vừa khó test.

  5. Câu 5 Facade khác Mediator ở điểm nào?

    Mediator là trung tâm liên lạc mà mọi bên đều biết và gửi tin qua đó. Facade chỉ là một lối tắt đặt phía trước, và các hệ con hoàn toàn không hay biết gì về nó.

  6. Câu 6 Vì sao nên truyền các hệ con vào CheckoutFacade qua constructor thay vì để facade tự tạo chúng?

    Khi hệ con được truyền vào, bài test chỉ cần đưa vào các bản giả rồi xem facade có gọi đúng thứ tự và bù trừ đúng khi lỗi hay không. Cách truyền này không làm code chạy nhanh hơn chút nào.
