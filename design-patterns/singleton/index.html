Creational pattern

Singleton

Singleton bảo đảm một lớp chỉ có đúng một đối tượng, thường gọi là instance, trong cả process, và mọi nơi đều lấy nó qua cùng một lối. Pattern này giải quyết được một vấn đề có thật, nhưng cũng là pattern dễ bị lạm dụng nhất, vì phần lớn trường hợp bạn chỉ cần tạo một đối tượng rồi truyền nó vào là đủ.

Bài toán

Hãy hình dung một ứng dụng backend chạy ba service trong cùng một process là đơn hàng, thanh toán và báo cáo. Cả ba cùng đọc ghi một cơ sở dữ liệu thông qua pool kết nối. Pool mở sẵn 10 kết nối rồi cho các truy vấn mượn lại, nhờ vậy truy vấn nào cũng không phải mở kết nối mới.

Thông sốGiá trị
Số kết nối tối đa cơ sở dữ liệu cho phép20
Số kết nối mỗi pool mở sẵn10
Số service cần truy vấn3

Ba service dùng chung một pool là đủ. Nếu mỗi service tự tạo pool riêng, ba pool sẽ đòi 30 kết nối, trong khi cơ sở dữ liệu chỉ cho phép 20.

Khi chưa có Singleton

Cách viết tự nhiên nhất là để mỗi service tự gọi ConnectionPool(DB) trong constructor của mình:

// Khi chưa có Singleton: mỗi service tự tạo pool kết nối của riêng nó.
// Chạy: node before.ts   (Node 22.18 trở lên chạy thẳng TypeScript)

class Database {
  static readonly MAX_CONNECTIONS = 20;
  used = 0;

  open(count: number): void {
    if (this.used + count > Database.MAX_CONNECTIONS) {
      throw new Error(`hết cổng (đang dùng ${this.used}/${Database.MAX_CONNECTIONS}, cần thêm ${count})`);
    }
    this.used += count;
  }
}

class ConnectionPool {
  static created = 0;
  readonly id: number;

  constructor(db: Database, size = 10) {
    this.id = ++ConnectionPool.created;
    db.open(size); // mở sẵn `size` kết nối tới cơ sở dữ liệu
  }
}

const db = new Database();

// Mỗi service tự tạo pool, nên ba pool cần 30 kết nối trong khi DB chỉ cho 20.
class OrderService {
  pool = new ConnectionPool(db);
}

class PaymentService {
  pool = new ConnectionPool(db);
}

class ReportService {
  pool = new ConnectionPool(db);
}

const services: [string, new () => { pool: ConnectionPool }][] = [
  ["Đơn hàng", OrderService],
  ["Thanh toán", PaymentService],
  ["Báo cáo", ReportService],
];
for (const [name, Service] of services) {
  try {
    const { pool } = new Service();
    console.log(`${name.padEnd(10)} -> pool #${pool.id}, cổng đang dùng ${db.used}/${Database.MAX_CONNECTIONS}`);
  } catch (error) {
    console.log(`${name.padEnd(10)} -> LỖI: ${(error as Error).message}`);
  }
}
console.log(`Đã tạo ${ConnectionPool.created} pool cho 3 service`);

Chạy thử sẽ thấy service thứ ba hỏng:

Đơn hàng   -> pool #1, cổng đang dùng 10/20
Thanh toán -> pool #2, cổng đang dùng 20/20
Báo cáo    -> LỖI: hết cổng (đang dùng 20/20, cần thêm 10)
Đã tạo 3 pool cho 3 service
  • Tài nguyên dùng chung bị phung phí. Pool nào cũng giữ 10 kết nối, kể cả khi service của nó gần như không dùng tới, nên đến service thứ ba thì không còn cổng nào để mở.
  • Lỗi phụ thuộc vào thứ tự khởi động. Service nào khởi tạo sau cùng thì hỏng, nên chỉ cần đổi thứ tự import là lỗi chuyển sang chỗ khác.
  • Cấu hình bị rải rác khắp nơi. Kích thước pool, timeout và chuỗi kết nối lặp lại ở mọi chỗ tạo pool, nên sửa chỗ này rất dễ quên chỗ kia.

Lời giải

Ta gom chỗ tạo pool về một hàm duy nhất. Lần gọi đầu tiên tạo pool rồi giữ nó lại, còn mọi lần gọi sau đều trả về đúng đối tượng đã giữ. Trong Python, cách tự nhiên nhất là một biến cấp module đi cùng hàm get_pool(). Trong TypeScript, cách kinh điển là constructor private kèm phương thức tĩnh getInstance().

singleton.pypython3 singleton.py
"""Singleton: cả process dùng chung đúng một pool kết nối.

Chạy: python3 singleton.py
"""
import threading


class Database:
    MAX_CONNECTIONS = 20

    def __init__(self) -> None:
        self.used = 0

    def open(self, count: int) -> None:
        if self.used + count > self.MAX_CONNECTIONS:
            raise RuntimeError(f"hết cổng (đang dùng {self.used}/{self.MAX_CONNECTIONS}, cần thêm {count})")
        self.used += count


class ConnectionPool:
    created = 0

    def __init__(self, db: Database, size: int = 10) -> None:
        ConnectionPool.created += 1
        self.id = ConnectionPool.created
        db.open(size)


DB = Database()

# Singleton theo kiểu Python: một biến cấp module giữ instance duy nhất.
_pool: ConnectionPool | None = None
_lock = threading.Lock()


def get_pool() -> ConnectionPool:
    """Lần gọi đầu tạo pool, mọi lần sau trả lại đúng đối tượng đó."""
    global _pool
    if _pool is None:
        with _lock:  # hai thread gọi cùng lúc vẫn chỉ tạo một pool
            if _pool is None:
                _pool = ConnectionPool(DB)
    return _pool


class OrderService:
    def __init__(self) -> None:
        self.pool = get_pool()


class PaymentService:
    def __init__(self) -> None:
        self.pool = get_pool()


class ReportService:
    def __init__(self) -> None:
        self.pool = get_pool()


if __name__ == "__main__":
    kinds = [("Đơn hàng", OrderService), ("Thanh toán", PaymentService), ("Báo cáo", ReportService)]
    services = []
    for name, kind in kinds:
        services.append(kind())
        print(f"{name:<10} -> pool #{services[-1].pool.id}, cổng đang dùng {DB.used}/{Database.MAX_CONNECTIONS}")
    same = all(s.pool is services[0].pool for s in services)
    print(f"Đã tạo {ConnectionPool.created} pool cho 3 service; cùng một object: {'có' if same else 'không'}")
singleton.tsnode singleton.ts
// Singleton: cả process dùng chung đúng một pool kết nối.
// Chạy: node singleton.ts   (Node 22.18 trở lên chạy thẳng TypeScript)

class Database {
  static readonly MAX_CONNECTIONS = 20;
  used = 0;

  open(count: number): void {
    if (this.used + count > Database.MAX_CONNECTIONS) {
      throw new Error(`hết cổng (đang dùng ${this.used}/${Database.MAX_CONNECTIONS}, cần thêm ${count})`);
    }
    this.used += count;
  }
}

const db = new Database();

class ConnectionPool {
  static created = 0;
  private static instance: ConnectionPool | null = null;
  readonly id: number;

  // private: code bên ngoài không gọi được `new ConnectionPool()`.
  private constructor(size = 10) {
    this.id = ++ConnectionPool.created;
    db.open(size);
  }

  // Lần gọi đầu tạo pool, mọi lần sau trả lại đúng đối tượng đó.
  // JavaScript chạy một luồng, nên không cần khoá như bản Python.
  static getInstance(): ConnectionPool {
    if (ConnectionPool.instance === null) ConnectionPool.instance = new ConnectionPool();
    return ConnectionPool.instance;
  }
}

class OrderService {
  pool = ConnectionPool.getInstance();
}

class PaymentService {
  pool = ConnectionPool.getInstance();
}

class ReportService {
  pool = ConnectionPool.getInstance();
}

const services: { pool: ConnectionPool }[] = [];
const kinds: [string, new () => { pool: ConnectionPool }][] = [
  ["Đơn hàng", OrderService],
  ["Thanh toán", PaymentService],
  ["Báo cáo", ReportService],
];
for (const [name, Service] of kinds) {
  services.push(new Service());
  console.log(`${name.padEnd(10)} -> pool #${services.at(-1)!.pool.id}, cổng đang dùng ${db.used}/${Database.MAX_CONNECTIONS}`);
}
const same = services.every((s) => s.pool === services[0].pool);
console.log(`Đã tạo ${ConnectionPool.created} pool cho 3 service; cùng một object: ${same ? "có" : "không"}`);

Khi nào dùng

  • Bạn cần đúng một bản trong process vì nó giữ tài nguyên có giới hạn hoặc trạng thái phải thống nhất. Pool kết nối, cache dùng chung, hàng đợi ghi log hay client của một dịch vụ giới hạn số kết nối là những ví dụ điển hình.
  • Tạo nó rất tốn kém, chẳng hạn phải đọc cấu hình, mở kết nối hay nạp mô hình, trong khi mọi nơi đều dùng chung được một bản.
  • Bạn đang viết thư viện hoặc một script nhỏ, nơi không có chỗ nào đóng vai composition root để tạo đối tượng rồi truyền đi.

Khi nào không nên

Phần này quan trọng không kém phần trên. Singleton thực chất là một biến toàn cục có kiểm soát, nên nó mang theo đủ mọi vấn đề của biến toàn cục:

  • Phụ thuộc bị giấu đi. Nhìn chữ ký OrderService(), bạn không biết nó cần cơ sở dữ liệu, phải đọc tới dòng get_pool() bên trong mới thấy.
  • Code trở nên khó test. Khi service tự gọi get_pool(), test không thay được pool thật bằng pool giả. Trạng thái còn dính từ test này sang test khác, vì instance sống suốt process.
  • Về sau rất khó thay đổi. Đến ngày cần hai pool, một để ghi và một để đọc từ bản sao, bạn sẽ phải sửa mọi chỗ đang gọi get_pool().
  • Giả định "chỉ có một" hiếm khi đúng mãi. Chỉ cần cấu hình theo tenant, theo vùng hay theo môi trường test là giả định ấy đã bị phá.

Vì thế, cách được dùng nhiều hơn là tạo đúng một pool ở composition root, tức hàm main, file khởi động hay DI container với scope singleton, rồi truyền nó vào constructor của từng service. Hệ thống vẫn chỉ có một pool, nhưng phụ thuộc giờ hiện rõ và test truyền được pool giả vào. Đoạn code dưới đây làm đúng như vậy.

di.pypython3 di.py
"""Cách thường dùng hơn Singleton: tạo đúng một pool ở composition root rồi truyền vào.

Chạy: python3 di.py
"""
from typing import Protocol


class Database:
    MAX_CONNECTIONS = 20

    def __init__(self) -> None:
        self.used = 0

    def open(self, count: int) -> None:
        if self.used + count > self.MAX_CONNECTIONS:
            raise RuntimeError(f"hết cổng (đang dùng {self.used}/{self.MAX_CONNECTIONS}, cần thêm {count})")
        self.used += count


class Pool(Protocol):
    id: int

    def query(self, sql: str) -> list[dict]: ...


class ConnectionPool:
    created = 0

    def __init__(self, db: Database, size: int = 10) -> None:
        ConnectionPool.created += 1
        self.id = ConnectionPool.created
        db.open(size)

    def query(self, sql: str) -> list[dict]:
        return []


# Service không tự đi tìm pool: nó nhận pool qua constructor.
class OrderService:
    def __init__(self, pool: Pool) -> None:
        self.pool = pool


class PaymentService:
    def __init__(self, pool: Pool) -> None:
        self.pool = pool


class ReportService:
    def __init__(self, pool: Pool) -> None:
        self.pool = pool

    def daily(self) -> int:
        return len(self.pool.query("SELECT * FROM orders WHERE day = today"))


# Pool giả cho test: không mở kết nối nào.
class FakePool:
    id = 0

    def query(self, sql: str) -> list[dict]:
        return [{"id": 1}, {"id": 2}]


if __name__ == "__main__":
    # Composition root: chỗ duy nhất quyết định "chỉ có một pool".
    db = Database()
    pool = ConnectionPool(db)
    services = [
        ("Đơn hàng", OrderService(pool)),
        ("Thanh toán", PaymentService(pool)),
        ("Báo cáo", ReportService(pool)),
    ]
    for name, service in services:
        print(f"{name:<10} -> pool #{service.pool.id}, cổng đang dùng {db.used}/{Database.MAX_CONNECTIONS}")
    same = all(service.pool is pool for _, service in services)
    print(f"Đã tạo {ConnectionPool.created} pool cho 3 service; cùng một object: {'có' if same else 'không'}")
    print(f"Test với pool giả: ReportService đọc {ReportService(FakePool()).daily()} dòng, không mở kết nối nào")

// Chạy: node di.ts   (Node 22.18 trở lên chạy thẳng TypeScript)

class Database {
  static readonly MAX_CONNECTIONS = 20;
  used = 0;

  open(count: number): void {
    if (this.used + count > Database.MAX_CONNECTIONS) {
      throw new Error(`hết cổng (đang dùng ${this.used}/${Database.MAX_CONNECTIONS}, cần thêm ${count})`);
    }
    this.used += count;
  }
}

interface Pool {
  readonly id: number;
  query(sql: string): object[];
}

class ConnectionPool implements Pool {
  static created = 0;
  readonly id: number;

  constructor(db: Database, size = 10) {
    this.id = ++ConnectionPool.created;
    db.open(size);
  }

  query(sql: string): object[] {
    return [];
  }
}

// Service không tự đi tìm pool: nó nhận pool qua constructor.
class OrderService {
  readonly pool: Pool;
  constructor(pool: Pool) {
    this.pool = pool;
  }
}

class PaymentService {
  readonly pool: Pool;
  constructor(pool: Pool) {
    this.pool = pool;
  }
}

class ReportService {
  readonly pool: Pool;
  constructor(pool: Pool) {
    this.pool = pool;
  }

  daily(): number {
    return this.pool.query("SELECT * FROM orders WHERE day = today").length;
  }
}

// Pool giả cho test: không mở kết nối nào.

const pool = new ConnectionPool(db);

Dễ nhầm với

  • Biến toàn cục là họ hàng gần nhất. Singleton chỉ thêm vài lớp bảo vệ là tạo đúng một lần, tạo lười khi cần và không cho new từ bên ngoài, còn nhược điểm phụ thuộc ẩn thì vẫn nguyên đó.
  • Scope singleton của DI container cũng chỉ cho ra một instance, nhưng do container quyết định và tiêm vào. Bản thân lớp không biết mình là singleton, nên test vẫn thay được.
  • Lớp toàn phương thức tĩnh, hay một module toàn hàm, không có instance nào để truyền đi hay thay thế, và cũng không implement được interface. Singleton ít ra vẫn là một đối tượng.
  • Flyweight chia sẻ nhiều đối tượng nhỏ bất biến để tiết kiệm bộ nhớ, mỗi giá trị một bản. Singleton thì chỉ có đúng một đối tượng cho cả lớp.
  • Factory Method trông khá giống getInstance(), nhưng factory thường tạo đối tượng mới ở mỗi lần gọi, còn getInstance() lần nào cũng trả về cùng một đối tượng.

Ghi chú khi triển khai

  • Cẩn thận khi có nhiều thread. Nếu tạo lười trong môi trường nhiều thread, hai thread có thể cùng thấy _pool is None và tạo ra hai pool. Hãy dùng khoá như ví dụ, kiểm tra hai lần với khoá ở giữa, hoặc tạo sẵn ngay khi nạp module. JavaScript chạy một luồng nên không cần khoá, trừ khi bước khởi tạo là hàm async. Khi đó hãy giữ Promise của lần tạo đầu tiên chứ đừng giữ kết quả.
  • Mỗi process có một instance, chứ không phải cả hệ thống. Chạy bốn worker bằng gunicorn, PM2 hay cluster là có bốn process, tức bốn pool với tổng cộng 40 kết nối. Hãy tính giới hạn của cơ sở dữ liệu theo tổng số process, hoặc đặt một pooler dùng chung phía trước cơ sở dữ liệu.
  • Module trong Python và ES module vốn đã là singleton. Module chỉ chạy một lần rồi được cache, nên một biến cấp module là đủ, không cần lớp có __new__ hay metaclass. Riêng với Node, một package bị cài hai phiên bản sẽ cho ra hai instance.
  • Hãy chừa cho test một lối thoát. Nếu buộc phải dùng Singleton, hãy thêm hàm reset hoặc cho phép đặt instance từ bên ngoài khi test, và ở các lớp mới viết thì nhận nó qua tham số.
  • Đừng để Singleton giữ trạng thái theo người dùng. Giỏ hàng hay phiên đăng nhập mà nằm trong Singleton thì mọi request đều dùng chung một đối tượng, và dữ liệu của người này sẽ lẫn sang người khác.

Kiểm tra nhanh

Sáu câu hỏi ngắn để xem bạn đã nắm Singleton tới đâu. Chọn một đáp án, lời giải thích sẽ hiện ngay bên dưới.

  1. Câu 1 Khi chưa có Singleton, mỗi service tự tạo một pool 10 kết nối, còn cơ sở dữ liệu chỉ cho phép 20. Chuyện gì xảy ra với service khởi động thứ ba?

    Hai pool đầu đã giữ đủ 20 kết nối, nên pool thứ ba cần thêm 10 thì không còn cổng nào. Lỗi chỉ hiện ra ở service khởi động sau cùng, nên rất dễ tưởng nhầm là lỗi của riêng service đó.

  2. Câu 2 Sau khi có get_pool(), ba service lần lượt gọi nó. Bộ đếm sẽ hiện bao nhiêu pool và bao nhiêu cổng đang dùng?

    Lần gọi đầu tạo pool #1 và mở 10 kết nối. Hai lần sau nhận lại đúng đối tượng ấy, nên không có pool mới nào được tạo và số cổng vẫn đứng ở 10/20.

  3. Câu 3 Vì sao người ta thường tạo pool một lần ở composition root rồi truyền vào constructor, thay vì để service tự gọi get_pool()?

    Hệ thống vẫn chỉ có một pool, nhưng service không còn tự đi lấy nó nữa. Nhờ vậy nhìn constructor là biết service cần gì, và test thay được pool thật bằng pool giả, như ví dụ đọc 2 dòng mà không mở kết nối nào.

  4. Câu 4 Hàm get_pool() tạo pool một cách lười, trong một server chạy nhiều thread. Nếu không có khoá, điều gì có thể xảy ra?

    Kiểm tra rồi mới tạo là hai bước tách rời, nên hai thread có thể cùng lọt qua bước kiểm tra. Một chiếc khoá, hoặc tạo sẵn pool ngay khi nạp module, bảo đảm chỉ có một thread được tạo.

  5. Câu 5 Ứng dụng chạy bốn worker process, mỗi process dùng Singleton cho một pool 10 kết nối. Tổng cộng có bao nhiêu kết nối tới cơ sở dữ liệu?

    Singleton chỉ là duy nhất trong một process. Bốn worker là bốn process, nên có bốn pool với tổng cộng 40 kết nối, vượt xa giới hạn 20 nếu bạn không tính trước.

  6. Câu 6 Thứ nào dưới đây không nên đặt trong một Singleton?

    Singleton là một đối tượng dùng chung cho mọi request, nên giỏ hàng đặt trong đó sẽ bị mọi người dùng chung và dữ liệu của người này lẫn sang người khác. Pool kết nối và client dùng chung thì đúng là những thứ chỉ nên có một bản.
