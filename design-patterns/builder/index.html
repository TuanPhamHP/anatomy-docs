Creational pattern

Builder

Builder giúp bạn dựng một đối tượng phức tạp qua nhiều bước nhỏ, mỗi bước có một cái tên rõ ràng. Code gọi chỉ đặt những phần mình cần rồi gọi build() một lần, và đến lúc ấy builder mới kiểm tra cả bộ rồi trả về một sản phẩm hoàn chỉnh, không ai sửa được nữa.

Bài toán

API danh sách đơn hàng cho phép lọc, sắp xếp và phân trang. Mỗi màn hình lại dùng một tổ hợp khác nhau. Màn đối soát lọc theo trạng thái và khoảng ngày, màn chăm sóc khách lọc theo khách hàng, còn màn báo cáo thì sắp theo tổng tiền.

Thứ cần trả về là một câu SQL dùng dấu ?, kèm một danh sách tham số riêng để driver của cơ sở dữ liệu tự gắn giá trị vào.

Khi chưa có Builder

Cách làm thường gặp là viết một hàm nhận mọi thứ làm tham số, rồi nối chuỗi theo từng nhánh if:

"""Trước khi có Builder: một hàm nhận cả tá tham số và tự nối chuỗi SQL.

Chạy: python3 before.py
"""


def find_orders_sql(status=None, date_from=None, date_to=None, customer_id=None,
                    sort=None, desc=False, page=1, size=20):
    sql = "SELECT id, code, total FROM orders WHERE"
    if status:
        sql += f" status = '{status}'"
    if date_from:
        sql += f" AND created_at >= '{date_from}'"
    if date_to:
        sql += f" AND created_at < '{date_to}'"
    if customer_id:
        sql += f" AND customer_id = {customer_id}"
    if sort:
        sql += f" ORDER BY {sort}" + (" DESC" if desc else "")
    sql += f" LIMIT {size} OFFSET {(page - 1) * size}"
    return sql


# Không lọc trạng thái: "WHERE AND ..." là SQL sai, và giá trị bị dán thẳng vào chuỗi.
print(find_orders_sql(None, "2026-10-01", "2026-11-01", None, "created_at", True, 3, 20))
# Tám tham số theo vị trí: đổi chỗ page và size vẫn chạy, chỉ là ra trang khác.
print(find_orders_sql("paid", None, None, None, "created_at", True, 20, 3))

// Chạy: node before.ts

function findOrdersSql(
  status: string | null = null,
  dateFrom: string | null = null,
  dateTo: string | null = null,
  customerId: number | null = null,
  sort: string | null = null,
  desc = false,
  page = 1,
  size = 20,
): string {
  let sql = "SELECT id, code, total FROM orders WHERE";
  if (status) sql += ` status = '${status}'`;
  if (dateFrom) sql += ` AND created_at >= '${dateFrom}'`;
  if (dateTo) sql += ` AND created_at < '${dateTo}'`;
  if (customerId) sql += ` AND customer_id = ${customerId}`;
  if (sort) sql += ` ORDER BY ${sort}` + (desc ? " DESC" : "");
  sql += ` LIMIT ${size} OFFSET ${(page - 1) * size}`;
  return sql;
}

SELECT id, code, total FROM orders WHERE status = 'paid' ORDER BY created_at DESC LIMIT 3 OFFSET 57
  • Tám tham số truyền theo vị trí rất khó đọc. Nhìn lời gọi ở cuối file, không ai biết True, 3, 20 nghĩa là gì nếu không mở hàm ra đọc. Đổi chỗ trang với cỡ trang thì code vẫn chạy, chỉ có điều ra nhầm trang, như dòng thứ hai in LIMIT 3 OFFSET 57.
  • Ghép chuỗi theo nhánh rất dễ sai cú pháp. Chỉ cần không lọc trạng thái là câu SQL có ngay WHERE AND. Mỗi bộ lọc mới lại là một nhánh mới, và nhánh nào cũng phải tự nhớ khi nào dùng WHERE, khi nào dùng AND.
  • Giá trị bị dán thẳng vào câu SQL. Kiểu viết '{status}' mở đường cho SQL injection, và cơ sở dữ liệu cũng không dùng lại được câu đã chuẩn bị.
  • Không có chỗ nào kiểm tra cả bộ. Hàm không hề biết cỡ trang 500 là quá lớn, hay ngày bắt đầu đang nằm sau ngày kết thúc.

Lời giải

Mỗi phần của câu truy vấn trở thành một phương thức của OrderQueryBuilder, lớp đóng vai Builder. Đó là status(), created_between(), customer(), order_by() và page(). Phương thức nào cũng kiểm tra phần của mình, cất vào builder rồi trả về chính builder, nhờ vậy bạn gọi nối tiếp được.

Đến build(), builder kiểm tra những điều chỉ biết được khi đã có đủ cả bộ, ở đây là câu truy vấn đã được phân trang hay chưa. Sau đó nó ghép câu theo đúng ngữ pháp SQL và trả về một Query. Đó là Product, một đối tượng bất biến.

"""Builder: dựng câu truy vấn danh sách đơn hàng từng bước, kiểm tra rồi mới tạo Query.

Chạy: python3 builder.py
"""
from dataclasses import dataclass

SORTABLE = {"created_at", "total"}
MAX_SIZE = 100


# Product: câu truy vấn đã dựng xong. frozen=True nên không ai sửa được nữa.
@dataclass(frozen=True)
class Query:
    sql: str
    params: tuple


# Builder: gom từng phần. Mỗi hàm trả về chính builder để gọi nối tiếp.
class OrderQueryBuilder:
    def __init__(self) -> None:
        self._where: list[tuple[str, object]] = []
        self._order: str | None = None
        self._page: tuple[int, int] | None = None

    def status(self, value: str) -> "OrderQueryBuilder":
        self._where.append(("status = ?", value))
        return self

    def created_between(self, start: str, end: str) -> "OrderQueryBuilder":
        if start >= end:
            raise ValueError("ngày bắt đầu phải trước ngày kết thúc")
        self._where.append(("created_at >= ?", start))
        self._where.append(("created_at < ?", end))
        return self

    def customer(self, customer_id: int) -> "OrderQueryBuilder":
        self._where.append(("customer_id = ?", customer_id))
        return self

    def order_by(self, column: str, desc: bool = False) -> "OrderQueryBuilder":
        if column not in SORTABLE:  # tên cột không đi qua tham số được, nên chỉ nhận cột trong danh sách
            raise ValueError(f"không sắp xếp theo cột {column}")
        self._order = f"ORDER BY {column}" + (" DESC" if desc else "")
        return self

    def page(self, number: int, size: int) -> "OrderQueryBuilder":
        if number < 1 or not 1 <= size <= MAX_SIZE:
            raise ValueError(f"page từ 1, size từ 1 đến {MAX_SIZE}")
        self._page = (size, (number - 1) * size)
        return self

    def build(self) -> Query:
        # Kiểm tra cả bộ một lần, rồi mới ghép câu theo đúng ngữ pháp SQL.
        if self._page is None:
            raise ValueError("thiếu page(): danh sách đơn phải phân trang")
        lines = ["SELECT id, code, total FROM orders"]
        params: list[object] = []
        for i, (condition, value) in enumerate(self._where):
            lines.append(("WHERE " if i == 0 else "  AND ") + condition)
            params.append(value)
        if self._order:
            lines.append(self._order)
        lines.append("LIMIT ? OFFSET ?")
        params.extend(self._page)
        return Query("\n".join(lines), tuple(params))


def show(params: tuple) -> str:
    return "[" + ", ".join(f'"{p}"' if isinstance(p, str) else str(p) for p in params) + "]"


if __name__ == "__main__":
    builder = (
        OrderQueryBuilder()
        .status("paid")
        .created_between("2026-10-01", "2026-11-01")
        .order_by("created_at", desc=True)
    )
    try:
        builder.build()
    except ValueError as error:
        print(f"build() từ chối: {error}")

    query = builder.page(3, 20).build()
    print(query.sql)
    print("params =", show(query.params))

// Builder: dựng câu truy vấn danh sách đơn hàng từng bước, kiểm tra rồi mới tạo Query.
// Chạy: node builder.ts   (Node 22.18 trở lên chạy thẳng TypeScript)

const SORTABLE = new Set(["created_at", "total"]);
const MAX_SIZE = 100;

type Param = string | number;

// Product: câu truy vấn đã dựng xong, chỉ đọc.
interface Query {
  readonly sql: string;
  readonly params: readonly Param[];
}

// Builder: gom từng phần. Mỗi hàm trả về chính builder để gọi nối tiếp.
class OrderQueryBuilder {
  private where: [string, Param][] = [];
  private order: string | null = null;
  private paging: [number, number] | null = null;

  status(value: string): this {
    this.where.push(["status = ?", value]);
    return this;
  }

  createdBetween(start: string, end: string): this {
    if (start >= end) throw new Error("ngày bắt đầu phải trước ngày kết thúc");
    this.where.push(["created_at >= ?", start], ["created_at < ?", end]);
    return this;
  }

  customer(customerId: number): this {
    this.where.push(["customer_id = ?", customerId]);
    return this;
  }

  orderBy(column: string, desc = false): this {
    // Tên cột không đi qua tham số được, nên chỉ nhận cột trong danh sách.
    if (!SORTABLE.has(column)) throw new Error(`không sắp xếp theo cột ${column}`);
    this.order = `ORDER BY ${column}` + (desc ? " DESC" : "");
    return this;
  }

  page(num: number, size: number): this {
    if (num < 1 || size < 1 || size > MAX_SIZE) throw new Error(`page từ 1, size từ 1 đến ${MAX_SIZE}`);
    this.paging = [size, (num - 1) * size];
    return this;
  }

  build(): Query {
    // Kiểm tra cả bộ một lần, rồi mới ghép câu theo đúng ngữ pháp SQL.
    if (!this.paging) throw new Error("thiếu page(): danh sách đơn phải phân trang");
    const lines = ["SELECT id, code, total FROM orders"];
    const params: Param[] = [];
    this.where.forEach(([condition, value], i) => {
      lines.push((i === 0 ? "WHERE " : "  AND ") + condition);
      params.push(value);
    });
    if (this.order) lines.push(this.order);
    lines.push("LIMIT ? OFFSET ?");
    params.push(...this.paging);
    return Object.freeze({ sql: lines.join("\n"), params: Object.freeze(params) });
  }
}

const show = (params: readonly Param[]) =>
  "[" + params.map((p) => (typeof p === "string" ? `"${p}"` : String(p))).join(", ") + "]";

const builder = new OrderQueryBuilder()
  .status("paid")
  .createdBetween("2026-10-01", "2026-11-01")
  .orderBy("created_at", true);

try {
  builder.build();
} catch (error) {
  console.log(`build() từ chối: ${(error as Error).message}`);
}

const query = builder.page(3, 20).build();
console.log(query.sql);
console.log("params =", show(query.params));

Bản TypeScript đặt tên phương thức theo kiểu camelCase, chẳng hạn createdBetween() và orderBy().

Chạy thử, hai bản in ra giống hệt nhau. Lần build() đầu tiên bị từ chối vì chưa gọi page(), nên không có Query nào được tạo ra. Sau khi gọi page(3, 20), builder trả về câu SQL sáu dòng cùng năm tham số, đúng như sáu bước trong hình phía trên:

Khi nào dùng

  • Đối tượng có nhiều phần tuỳ chọn và nhiều tổ hợp hợp lệ. Câu truy vấn, request HTTP với header, query, body và timeout, email với người nhận, cc và đính kèm, báo cáo hay cấu hình của một client đều thuộc loại này.
  • Giữa các phần có những ràng buộc chỉ kiểm tra được khi đã có đủ cả bộ, chẳng hạn bắt buộc phân trang, ngày bắt đầu phải trước ngày kết thúc, hay có đính kèm thì phải có tên file.
  • Bạn muốn sản phẩm bất biến nhưng vẫn dựng dần được qua nhiều chỗ trong code.
  • Cùng một chuỗi bước cần dựng ra nhiều dạng sản phẩm, ví dụ một builder cho cú pháp Postgres và một builder cho MySQL dùng chung cách gọi.

Khi nào không nên

  • Đối tượng chỉ có ít trường và phần lớn là bắt buộc. Một constructor hay một dataclass với tham số đặt tên là đủ, ví dụ Money(amount=..., currency="VND").
  • Bạn chỉ khổ vì có nhiều tham số tuỳ chọn, chứ không cần kiểm tra chéo hay dựng qua nhiều bước. Khi đó tham số đặt tên có giá trị mặc định trong Python, hay một đối tượng options trong TypeScript, sẽ gọn hơn.
  • Thư viện bạn dùng đã có sẵn builder, như query builder của ORM hay builder của HTTP client. Hãy dùng nó thay vì viết lại.

Dễ nhầm với

  • Factory Method và Abstract Factory chọn loại đối tượng cần tạo rồi trả về ngay trong một lần gọi. Builder thì dựng một đối tượng qua nhiều bước rồi mới trả ra.
  • Fluent interface chỉ là kiểu viết gọi nối chuỗi như .a().b(). Builder hay dùng kiểu viết này, nhưng chuỗi map().filter() trên mảng thì không phải Builder, vì không có bước build() nào chốt lại sản phẩm.
  • Template Method cố định thứ tự các bước ngay trong lớp cha. Với Builder, code gọi tự chọn gọi bước nào và theo thứ tự nào, còn build() sẽ sắp lại cho đúng.
  • Prototype tạo đối tượng mới bằng cách sao chép một mẫu có sẵn chứ không dựng lại từ đầu.

Ghi chú khi triển khai

  • Thứ gì kiểm tra được ngay thì nên kiểm tra sớm, nên page(1, 500) báo lỗi ngay ở chính lời gọi đó. Chỉ những ràng buộc cần cả bộ mới để dành cho build().
  • Giá trị luôn đi qua tham số ?. Chỉ những phần không tham số hoá được, như tên cột để sắp xếp, mới được ghép thẳng vào câu, và chúng phải nằm trong danh sách cho phép.
  • Builder là nơi nắm ngữ pháp, nên gọi page() trước status() vẫn ra câu đúng. Lý do là build() luôn ghép WHERE trước, rồi đến ORDER BY, cuối cùng là LIMIT, giống như trong hình mỗi thanh chữ có sẵn hàng riêng của nó.
  • Hãy ghi rõ khi gọi lại một phương thức thì giá trị cũ bị thay hay được cộng dồn. Trong ví dụ, order_by() và page() thay giá trị cũ, còn các điều kiện lọc thì cộng thêm vào.
  • Builder có trạng thái và thay đổi được, nên đừng dùng chung một builder cho nhiều request. Thứ nên đem đi dùng chung là Query bất biến.

Kiểm tra nhanh

Sáu câu hỏi ngắn để xem bạn đã nắm Builder tới đâu. Chọn một đáp án, lời giải thích sẽ hiện ngay bên dưới.

  1. Câu 1 Sau khi gọi page(3, 20), hai tham số cuối của Query là gì?

    Trang 3 với cỡ trang 20 nghĩa là lấy 20 dòng và bỏ qua 40 dòng của hai trang đầu, nên LIMIT nhận 20 còn OFFSET nhận 40. Bản code cũ nhầm đúng ở chỗ này khi truyền tham số theo vị trí.

  2. Câu 2 Trong hình, build() được gọi khi chưa có page(). Chuyện gì xảy ra?

    Phân trang là ràng buộc của cả bộ, nên build() kiểm tra nó trước khi ghép câu. Thiếu page() thì builder từ chối hẳn chứ không tự đoán giá trị mặc định, vì một danh sách đơn không phân trang có thể kéo cả bảng về.

  3. Câu 3 Vì sao bản code cũ có thể sinh ra câu SQL chứa WHERE AND?

    Khi ghép chuỗi theo từng nhánh, nhánh nào cũng phải tự nhớ lúc nào dùng WHERE, lúc nào dùng AND. Builder gom các điều kiện lại và để build() ghép chúng theo đúng ngữ pháp một lần duy nhất.

  4. Câu 4 Trường hợp nào không cần đến Builder?

    Với ít trường và phần lớn là bắt buộc, một constructor hay dataclass với tham số đặt tên là đủ rõ ràng. Builder chỉ đáng giá khi có nhiều phần tuỳ chọn và có ràng buộc cần kiểm tra trên cả bộ.

  5. Câu 5 Gọi page(1, 500) thì builder nên báo lỗi vào lúc nào?

    Thứ gì kiểm tra được ngay thì nên kiểm tra sớm, để lỗi chỉ thẳng vào lời gọi sai. build() chỉ nên giữ những ràng buộc cần đủ cả bộ, như việc câu truy vấn đã được phân trang hay chưa.

  6. Câu 6 Chuỗi items.map(...).filter(...) trên một mảng có phải là Builder không?

    Gọi nối chuỗi chỉ là một kiểu viết, thường gọi là fluent interface. Builder hay dùng kiểu viết này, nhưng điều làm nên Builder là gom các phần qua nhiều bước rồi chốt lại thành một sản phẩm ở build().
