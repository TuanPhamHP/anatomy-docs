Behavioral pattern

State

State cho phép một đối tượng đổi cách cư xử khi trạng thái bên trong của nó thay đổi. Mỗi trạng thái là một lớp riêng giữ trọn luật của chính nó, còn đối tượng chỉ việc chuyển từng yêu cầu cho trạng thái hiện tại, nên nhìn từ bên ngoài, nó như thể đã đổi sang một lớp khác.

Bài toán

Hãy xét một hồ sơ đề nghị mua hàng. Hồ sơ đi qua bốn trạng thái là Nháp, Chờ duyệt, Đã duyệt và Bị từ chối, còn người dùng có bốn thao tác là gửi duyệt, duyệt, từ chối và sửa lại. Cùng một thao tác cho ra kết quả khác nhau tuỳ trạng thái, và phần lớn các ô trong bảng dưới đây là những thao tác không được phép.

Trạng tháigửi duyệtduyệttừ chốisửa lại
Nháp→ Chờ duyệtbị chặnbị chặnbị chặn
Chờ duyệtbị chặn→ Đã duyệt→ Bị từ chốibị chặn
Đã duyệtbị chặnbị chặnbị chặnbị chặn
Bị từ chốibị chặnbị chặnbị chặn→ Nháp

Khi một thao tác bị chặn, hệ thống phải báo đúng lý do của trạng thái lúc đó. Chẳng hạn với hồ sơ đã duyệt, lý do là hồ sơ không đổi được nữa.

Khi chưa có State

Cách làm thường gặp là lưu trạng thái trong một chuỗi và để mỗi thao tác tự hỏi xem mình đang ở đâu.

// Khi chưa có State: mỗi thao tác tự kiểm tra trạng thái bằng một switch.
type Status = "draft" | "pending" | "approved" | "rejected";

const NAMES: Record<Status, string> = { draft: "Nháp", pending: "Chờ duyệt", approved: "Đã duyệt", rejected: "Bị từ chối" };

class ActionRefused extends Error {}

class PurchaseRequest {
  status: Status = "draft";

  submit(): void {
    switch (this.status) {
      case "draft": this.status = "pending"; break;
      case "pending": throw new ActionRefused("hồ sơ đang chờ duyệt");
      case "approved": throw new ActionRefused("hồ sơ đã duyệt, không đổi được nữa");
      case "rejected": throw new ActionRefused("hồ sơ bị từ chối, cần sửa lại trước");
    }
  }

  approve(): void {
    switch (this.status) {
      case "pending": this.status = "approved"; break;
      case "draft": throw new ActionRefused("hồ sơ nháp chưa được gửi đi");
      case "approved": throw new ActionRefused("hồ sơ đã duyệt, không đổi được nữa");
      case "rejected": throw new ActionRefused("hồ sơ bị từ chối, cần sửa lại trước");
    }
  }

  reject(): void {
    switch (this.status) {
      case "pending": this.status = "rejected"; break;
      case "draft": throw new ActionRefused("hồ sơ nháp chưa được gửi đi");
      case "approved": throw new ActionRefused("hồ sơ đã duyệt, không đổi được nữa");
      case "rejected": throw new ActionRefused("hồ sơ bị từ chối, cần sửa lại trước");
    }
  }

  revise(): void {
    switch (this.status) {
      case "rejected": this.status = "draft"; break;
      case "draft": throw new ActionRefused("hồ sơ nháp chưa được gửi đi");
      case "pending": throw new ActionRefused("hồ sơ đang chờ duyệt");
      case "approved": throw new ActionRefused("hồ sơ đã duyệt, không đổi được nữa");
    }
  }
  // Muốn thêm trạng thái "Đã huỷ" thì phải sửa cả bốn hàm trên.
}

const request = new PurchaseRequest();
const steps: [string, () => void][] = [
  ["gửi duyệt", () => request.submit()],
  ["từ chối", () => request.reject()],
  ["sửa lại", () => request.revise()],
  ["gửi duyệt", () => request.submit()],
  ["duyệt", () => request.approve()],
  ["gửi duyệt", () => request.submit()],
];
for (const [label, action] of steps) {
  const before = NAMES[request.status];
  let result: string;
  try {
    action();
    result = NAMES[request.status];
  } catch (refused) {
    if (!(refused instanceof ActionRefused)) throw refused;
    result = `bị chặn: ${refused.message}`;
  }
  console.log(`${before.padEnd(10)} + ${label.padEnd(9)} → ${result}`);
}
  • Luật của một trạng thái nằm rải rác khắp nơi. Muốn biết hồ sơ đang chờ duyệt làm được gì, bạn phải đọc cả bốn hàm.
  • Thêm một trạng thái là phải sửa mọi thao tác. Thêm trạng thái Đã huỷ nghĩa là thêm một nhánh vào từng hàm. Quên một nhánh là sinh ra lỗi im lặng, vì thao tác lẽ ra bị chặn lại chạy qua.
  • Lý do bị chặn bị chép đi chép lại. Cùng một câu báo lỗi xuất hiện ở nhiều chỗ, và lâu dần chúng lệch nhau.
  • Tên trạng thái là chuỗi gõ tay. Gõ nhầm "pending" thành "pendng" không báo lỗi lúc viết code mà chỉ lộ ra khi chạy.

Lời giải

Ta định nghĩa một interface State có đủ bốn thao tác, và mặc định thao tác nào cũng bị chặn. Mỗi trạng thái cụ thể, thường gọi là ConcreteState, là một lớp con chỉ viết lại những thao tác nó chấp nhận, và chính nó quyết định trạng thái kế tiếp.

Hồ sơ đóng vai Context. Nó giữ một đối tượng trạng thái và chuyển mọi thao tác cho đối tượng đó, nên trong hồ sơ không còn câu if nào hỏi về trạng thái.

"""State: mỗi trạng thái của hồ sơ là một lớp, tự quyết định thao tác nào được làm.

Chạy: python3 state.py
"""
from __future__ import annotations


class ActionRefused(Exception):
    pass


# State là interface chung. Mặc định mọi thao tác đều bị chặn,
# mỗi trạng thái chỉ viết lại những thao tác nó nhận.
class State:
    name = ""
    refusal = ""

    def submit(self, request: PurchaseRequest) -> None:
        raise ActionRefused(self.refusal)

    def approve(self, request: PurchaseRequest) -> None:
        raise ActionRefused(self.refusal)

    def reject(self, request: PurchaseRequest) -> None:
        raise ActionRefused(self.refusal)

    def revise(self, request: PurchaseRequest) -> None:
        raise ActionRefused(self.refusal)


# Mỗi ConcreteState giữ trọn luật của một trạng thái.
class Draft(State):
    name = "Nháp"
    refusal = "hồ sơ nháp chưa được gửi đi"

    def submit(self, request: PurchaseRequest) -> None:
        request.state = Pending()


class Pending(State):
    name = "Chờ duyệt"
    refusal = "hồ sơ đang chờ duyệt"

    def approve(self, request: PurchaseRequest) -> None:
        request.state = Approved()

    def reject(self, request: PurchaseRequest) -> None:
        request.state = Rejected()


class Approved(State):
    name = "Đã duyệt"
    refusal = "hồ sơ đã duyệt, không đổi được nữa"


class Rejected(State):
    name = "Bị từ chối"
    refusal = "hồ sơ bị từ chối, cần sửa lại trước"

    def revise(self, request: PurchaseRequest) -> None:
        request.state = Draft()


# Context là hồ sơ đề nghị mua hàng. Nó không hỏi mình đang ở trạng thái nào,
# mà chỉ chuyển thao tác cho trạng thái hiện tại.
class PurchaseRequest:
    def __init__(self) -> None:
        self.state: State = Draft()

    def submit(self) -> None:
        self.state.submit(self)

    def approve(self) -> None:
        self.state.approve(self)

    def reject(self) -> None:
        self.state.reject(self)

    def revise(self) -> None:
        self.state.revise(self)


if __name__ == "__main__":
    request = PurchaseRequest()
    steps = [
        ("gửi duyệt", request.submit),
        ("từ chối", request.reject),
        ("sửa lại", request.revise),
        ("gửi duyệt", request.submit),
        ("duyệt", request.approve),
        ("gửi duyệt", request.submit),
    ]
    for label, action in steps:
        before = request.state.name
        try:
            action()
            result = request.state.name
        except ActionRefused as refused:
            result = f"bị chặn: {refused}"
        print(f"{before:<10} + {label:<9} → {result}")

// State: mỗi trạng thái của hồ sơ là một lớp, tự quyết định thao tác nào được làm.
// Chạy: node state.ts   (Node 22.18 trở lên chạy thẳng TypeScript)

class ActionRefused extends Error {}

// State là interface chung. Mặc định mọi thao tác đều bị chặn,
// mỗi trạng thái chỉ viết lại những thao tác nó nhận.
abstract class State {
  abstract readonly name: string;
  abstract readonly refusal: string;

  submit(request: PurchaseRequest): void {
    throw new ActionRefused(this.refusal);
  }

  approve(request: PurchaseRequest): void {
    throw new ActionRefused(this.refusal);
  }

  reject(request: PurchaseRequest): void {
    throw new ActionRefused(this.refusal);
  }

  revise(request: PurchaseRequest): void {
    throw new ActionRefused(this.refusal);
  }
}

Chạy thử, bản Python và bản TypeScript in ra cùng một kết quả, và kết quả này cũng giống hệt bản trước khi có State:

Nháp       + gửi duyệt → Chờ duyệt
Chờ duyệt  + từ chối   → Bị từ chối
Bị từ chối + sửa lại   → Nháp
Nháp       + gửi duyệt → Chờ duyệt
Chờ duyệt  + duyệt     → Đã duyệt
Đã duyệt   + gửi duyệt → bị chặn: hồ sơ đã duyệt, không đổi được nữa

Khi nào dùng

  • Khi một đối tượng có vòng đời rõ ràng và cách cư xử đổi theo từng chặng, như hồ sơ phê duyệt, đơn hàng đi từ lúc mới tạo, đã thanh toán, đang giao, đã giao cho tới đã huỷ, hay ticket hỗ trợ, hợp đồng, kết nối mạng.
  • Khi nhiều hàm cùng rẽ nhánh theo một biến trạng thái, và các nhánh đó cứ dài thêm mỗi lần có trạng thái mới.
  • Khi mỗi trạng thái có luật riêng đáng kể, chẳng hạn kiểm tra quyền, tính toán hay gửi thông báo lúc vào hoặc rời trạng thái.

Khi nào không nên

  • Nếu chỉ có hai, ba trạng thái với luật đơn giản, một câu if hoặc một bảng chuyển trạng thái sẽ ngắn và dễ đọc hơn. Bảng đó có thể chỉ là một dict ánh xạ từ cặp trạng thái và thao tác sang trạng thái kế tiếp.
  • Nếu các trạng thái không có hành vi riêng mà chỉ khác nhau ở cái nhãn, thì đó là dữ liệu, và một cột enum là đủ.
  • Nếu luồng phức tạp, có nhánh song song, có hẹn giờ và cần vẽ ra cho người khác duyệt, một thư viện state machine hoặc workflow engine sẽ hợp hơn là tự viết từng lớp.

Dễ nhầm với

  • Strategy có cấu trúc gần như y hệt, vì context cũng giữ một đối tượng và giao việc cho nó. Điểm khác nằm ở chỗ ai đổi đối tượng đó. Với Strategy, code bên ngoài chọn cách làm, còn với State, chính trạng thái hiện tại tự chuyển sang trạng thái kế.
  • Bảng chuyển trạng thái, tức state machine viết dưới dạng dữ liệu, chỉ trả lời câu hỏi đi đâu tiếp. State pattern giữ thêm cả hành vi của từng trạng thái, và hai cách này thường đi cùng nhau.
  • Command gói một thao tác thành đối tượng để xếp hàng hay hoàn tác. Ở đây thao tác vẫn là lời gọi hàm bình thường, thứ được gói lại là trạng thái.

Ghi chú khi triển khai

  • Trong cơ sở dữ liệu, trạng thái vẫn nằm trong một cột chuỗi hoặc enum. Khi đọc hồ sơ lên, bạn dựng lại đối tượng trạng thái từ cột đó, và khi lưu thì ghi ngược tên trạng thái ra.
  • Các lớp trạng thái trong ví dụ không có dữ liệu riêng, nên mọi hồ sơ có thể dùng chung một instance thay vì tạo mới mỗi lần chuyển.
  • Nếu hai người cùng bấm duyệt và từ chối một lúc, cả hai thao tác có thể cùng báo thành công. Để tránh chuyện đó, hãy đặt bước kiểm tra trạng thái và bước ghi trạng thái mới trong cùng một giao dịch, hoặc dùng cột phiên bản theo kiểu optimistic locking.
  • Thao tác bị chặn là lỗi nghiệp vụ chứ không phải lỗi hệ thống. Hãy trả về một mã rõ ràng như HTTP 409 kèm lý do của trạng thái, và ghi lại lịch sử mỗi lần chuyển trạng thái để tra cứu về sau.

Kiểm tra nhanh

Sáu câu hỏi ngắn để xem bạn đã nắm State tới đâu. Chọn một đáp án, lời giải thích sẽ hiện ngay bên dưới.

  1. Câu 1 Đơn hàng của bạn đi qua các trạng thái mới tạo, đã thanh toán, đang giao, đã giao và đã huỷ. Các hàm huỷ đơn, hoàn tiền và giao hàng đều mở đầu bằng một chuỗi if/elif dài hỏi đơn đang ở đâu. Pattern nào giúp gom luật của từng trạng thái về một chỗ?

    State biến mỗi trạng thái thành một lớp giữ trọn luật của nó, nên muốn biết đơn đang giao làm được gì, bạn chỉ cần đọc một lớp. Strategy có cấu trúc giống vậy nhưng dùng khi code bên ngoài chọn cách làm, chứ không phải khi đối tượng tự đi qua từng chặng.

  2. Câu 2 Trong ví dụ, lớp nào đóng vai Context?

    PurchaseRequest giữ đối tượng trạng thái hiện tại và chuyển mọi thao tác cho nó. State là interface chung, còn Pending là một trạng thái cụ thể.

  3. Câu 3 Hồ sơ đang ở trạng thái Đã duyệt, và người dùng bấm gửi duyệt thêm một lần nữa. Chuyện gì xảy ra?

    Approved không viết lại thao tác nào, nên mọi thao tác rơi vào hành vi mặc định là chặn kèm lý do của trạng thái này. Trong hình, phím chạm vào mặt trống của trống và trống không quay, còn Context không hề có câu if nào.

  4. Câu 4 Bạn cần thêm trạng thái Đã huỷ, cho phép huỷ khi hồ sơ đang là Nháp hoặc Chờ duyệt. Với cách viết theo State, bạn phải làm gì?

    Thêm trạng thái mới chỉ chạm tới đúng những trạng thái liên quan. Các trạng thái còn lại tự động chặn thao tác huỷ nhờ hành vi mặc định trong interface, và PurchaseRequest chỉ cần thêm một phương thức chuyển thao tác đi.

  5. Câu 5 State và Strategy có cấu trúc gần như giống nhau. Điểm khác chính giữa hai pattern là gì?

    Trong ví dụ, Pending.approve() tự gán request.state = Approved(), nên đối tượng tự chuyển chặng. Với Strategy, người dùng hay trang thanh toán mới là bên chọn cách tính, và cách tính không tự đổi sang cách khác.

  6. Câu 6 Khi nào một cột enum đơn giản là đủ, không cần đến State?

    Nếu trạng thái không kéo theo hành vi khác nhau thì đó chỉ là dữ liệu, và tạo một lớp cho mỗi nhãn chỉ làm code dài thêm. Ba trường hợp còn lại chính là lúc State phát huy tác dụng.
