Creational pattern

Factory Method

Factory Method để lớp cha viết sẵn quy trình làm việc với một đối tượng, còn bước tạo ra đối tượng đó thì giao cho một phương thức mà lớp con ghi đè. Quy trình vì thế luôn giữ nguyên, và mỗi lớp con chỉ cần quyết định mình tạo loại nào.

Bài toán

Khi đơn hàng đã giao xong, hệ thống bán hàng cần báo cho khách biết. Nội dung thì giống nhau, nhưng mỗi kênh lại gửi theo một kiểu riêng:

KênhGửi tớiCách gửiPhí
Emaillan@example.comThêm tiêu đề, giữ nguyên nội dung20 ₫
SMS0901234567Bỏ dấu, mỗi tin 160 ký tự500 ₫ một tin
PushMáy app-7f3aRút gọn còn 28 ký tự cho màn hình khoá0 ₫

Ngoài khác biệt đó ra, kênh nào cũng đi qua đúng một quy trình: tạo một bộ gửi, đưa nội dung vào, gửi đi rồi ghi lại kết quả. Sau này chắc chắn sẽ còn thêm kênh mới, chẳng hạn Zalo hay webhook.

Khi chưa có Factory Method

Cách viết thường gặp là dồn hết vào một hàm notify(), để nó tự rẽ nhánh theo tên kênh và tự lo từng kiểu gửi:

before.pypython3 before.py
"""Trước khi có Factory Method: dịch vụ thông báo tự lo mọi kênh trong một hàm.

Chạy: python3 before.py
"""
import math
import unicodedata


def no_accents(text: str) -> str:
    text = text.replace("đ", "d").replace("Đ", "D")
    return "".join(c for c in unicodedata.normalize("NFD", text) if not unicodedata.combining(c))


class NotificationService:
    def notify(self, user: dict, text: str, channel: str) -> str:
        # Mỗi kênh mới là một nhánh mới trong hàm đang chạy ổn.
        if channel == "email":
            return f"Email → {user['email']}: [Cập nhật đơn hàng] {text} ({len(text)} ký tự, phí 20 ₫)"
        elif channel == "sms":
            plain = no_accents(text)
            parts = math.ceil(len(plain) / 160)
            return f"SMS → {user['phone']}: {plain} ({parts} tin, phí {parts * 500} ₫)"
        elif channel == "push":
            short = text if len(text) <= 28 else text[:28].rsplit(" ", 1)[0] + "…"
            return f"Push → máy {user['device']}: {short} (phí 0 ₫)"
        else:
            raise ValueError(f'chưa hỗ trợ kênh "{channel}"')


if __name__ == "__main__":
    service = NotificationService()
    user = {"email": "lan@example.com", "phone": "0901234567", "device": "app-7f3a"}
    text = "Đơn DH-2041 đã giao thành công. Cảm ơn bạn!"
    for channel in ["email", "sms", "push"]:
        print(service.notify(user, text, channel))
    try:
        service.notify(user, text, "zalo")
    except ValueError as error:
        print(f"Lỗi: {error}, phải mở NotificationService ra sửa")

// Trước khi có Factory Method: dịch vụ thông báo tự lo mọi kênh trong một hàm.
// Chạy: node before.ts

const noAccents = (text: string) =>
  text.replace(/đ/g, "d").replace(/Đ/g, "D").normalize("NFD").replace(/\p{M}/gu, "");

type User = { email: string; phone: string; device: string };

class NotificationService {
  notify(user: User, text: string, channel: string): string {
    // Mỗi kênh mới là một nhánh mới trong hàm đang chạy ổn.
    if (channel === "email") {
      return `Email → ${user.email}: [Cập nhật đơn hàng] ${text} (${text.length} ký tự, phí 20 ₫)`;
    } else if (channel === "sms") {
      const plain = noAccents(text);
      const parts = Math.ceil(plain.length / 160);
      return `SMS → ${user.phone}: ${plain} (${parts} tin, phí ${parts * 500} ₫)`;
    } else if (channel === "push") {
      const cut = text.slice(0, 28);
      const short = text.length <= 28 ? text : cut.slice(0, cut.lastIndexOf(" ")) + "…";
      return `Push → máy ${user.device}: ${short} (phí 0 ₫)`;
    }
    throw new Error(`chưa hỗ trợ kênh "${channel}"`);
  }
}

const service = new NotificationService();
const user: User = { email: "lan@example.com", phone: "0901234567", device: "app-7f3a" };
const text = "Đơn DH-2041 đã giao thành công. Cảm ơn bạn!";
for (const channel of ["email", "sms", "push"]) {
  console.log(service.notify(user, text, channel));
}
try {
  service.notify(user, text, "zalo");
} catch (error) {
  console.log(`Lỗi: ${(error as Error).message}, phải mở NotificationService ra sửa`);
}

  • Thêm kênh là phải sửa phần lõi. Mỗi kênh mới là thêm một nhánh elif vào hàm đang chạy ổn, và mọi kênh cũ lại phải test lại từ đầu.
  • Quy trình chung bị kẹp giữa các nhánh. Muốn thêm bước ghi log hay thử lại cho mọi kênh, bạn phải chèn vào từng nhánh một.
  • Tên kênh chỉ là một chuỗi. Gõ nhầm thành "Sms" hay gọi một kênh chưa hỗ trợ thì chỉ đến lúc chạy mới lộ ra, giống dòng cuối ở trên.

Lời giải

Ta tách quy trình gửi ra khỏi bước tạo bộ gửi. Kênh nào cũng tạo ra một bộ gửi theo cùng một interface là Sender, chỉ có một phương thức send(), và đó là Product. Lớp cha Notifier đóng vai Creator, viết sẵn notify() để gọi create_sender() rồi dùng thứ nó trả về.

Chính create_sender() là factory method. Lớp cha chỉ khai báo nó, còn mỗi lớp con như EmailNotifier, SmsNotifier hay PushNotifier ghi đè bằng đúng một dòng tạo đối tượng của mình.

factory.pypython3 factory.py
"""Factory Method: lớp cha giữ quy trình gửi thông báo, lớp con quyết định tạo Sender nào.

Chạy: python3 factory.py
"""
import math
import unicodedata
from abc import ABC, abstractmethod
from dataclasses import dataclass


@dataclass(frozen=True)
class User:
    email: str
    phone: str
    device: str


def no_accents(text: str) -> str:
    text = text.replace("đ", "d").replace("Đ", "D")
    return "".join(c for c in unicodedata.normalize("NFD", text) if not unicodedata.combining(c))


# Product: interface chung của mọi Sender. Code gọi chỉ cần biết send().
class Sender(ABC):
    @abstractmethod
    def send(self, user: User, text: str) -> str: ...


# Concrete products: mỗi kênh gửi theo cách riêng.
class EmailSender(Sender):
    def send(self, user: User, text: str) -> str:
        return f"{user.email}: [Cập nhật đơn hàng] {text} ({len(text)} ký tự, phí 20 ₫)"


class SmsSender(Sender):
    def send(self, user: User, text: str) -> str:
        plain = no_accents(text)  # tin không dấu: 160 ký tự một tin
        parts = math.ceil(len(plain) / 160)
        return f"{user.phone}: {plain} ({parts} tin, phí {parts * 500} ₫)"


class PushSender(Sender):
    def send(self, user: User, text: str) -> str:
        short = text if len(text) <= 28 else text[:28].rsplit(" ", 1)[0] + "…"  # màn hình khoá hiện 28 ký tự
        return f"máy {user.device}: {short} (phí 0 ₫)"


# Creator: notify() là quy trình cố định. Chỉ create_sender() để lớp con quyết định.
class Notifier(ABC):
    @abstractmethod
    def create_sender(self) -> Sender: ...  # factory method

    def notify(self, user: User, text: str) -> str:
        sender = self.create_sender()
        result = sender.send(user, text)
        return f"{type(self).__name__} tạo {type(sender).__name__} → {result}"


# Concrete creators: mỗi lớp con chỉ viết đúng một dòng tạo object.
class EmailNotifier(Notifier):
    def create_sender(self) -> Sender:
        return EmailSender()


class SmsNotifier(Notifier):
    def create_sender(self) -> Sender:
        return SmsSender()


class PushNotifier(Notifier):
    def create_sender(self) -> Sender:
        return PushSender()


# Biến thể đơn giản hơn: một hàm factory chọn lớp theo tên kênh, không cần lớp con.
SENDERS: dict[str, type[Sender]] = {"email": EmailSender, "sms": SmsSender, "push": PushSender}


def sender_for(channel: str) -> Sender:
    return SENDERS[channel]()


if __name__ == "__main__":
    user = User(email="lan@example.com", phone="0901234567", device="app-7f3a")
    text = "Đơn DH-2041 đã giao thành công. Cảm ơn bạn!"
    for notifier in [EmailNotifier(), SmsNotifier(), PushNotifier()]:
        print(notifier.notify(user, text))
    print(f'Hàm factory với "sms" → {type(sender_for("sms")).__name__}')

// Factory Method: lớp cha giữ quy trình gửi thông báo, lớp con quyết định tạo Sender nào.
// Chạy: node factory.ts   (Node 22.18 trở lên chạy thẳng TypeScript)

interface User {
  email: string;
  phone: string;
  device: string;
}

const noAccents = (text: string) =>
  text.replace(/đ/g, "d").replace(/Đ/g, "D").normalize("NFD").replace(/\p{M}/gu, "");

// Product: interface chung của mọi Sender. Code gọi chỉ cần biết send().
interface Sender {
  send(user: User, text: string): string;
}

// Concrete products: mỗi kênh gửi theo cách riêng.
class EmailSender implements Sender {
  send(user: User, text: string): string {
    return `${user.email}: [Cập nhật đơn hàng] ${text} (${text.length} ký tự, phí 20 ₫)`;
  }
}

class SmsSender implements Sender {
  send(user: User, text: string): string {
    const plain = noAccents(text); // tin không dấu: 160 ký tự một tin
    const parts = Math.ceil(plain.length / 160);
    return `${user.phone}: ${plain} (${parts} tin, phí ${parts * 500} ₫)`;
  }
}

class PushSender implements Sender {
  send(user: User, text: string): string {
    const cut = text.slice(0, 28);
    const short = text.length <= 28 ? text : cut.slice(0, cut.lastIndexOf(" ")) + "…"; // màn hình khoá hiện 28 ký tự
    return `máy ${user.device}: ${short} (phí 0 ₫)`;
  }
}

// Creator: notify() là quy trình cố định. Chỉ createSender() để lớp con quyết định.
abstract class Notifier {
  abstract createSender(): Sender; // factory method

  notify(user: User, text: string): string {
    const sender = this.createSender();
    const result = sender.send(user, text);
    return `${this.constructor.name} tạo ${sender.constructor.name} → ${result}`;
  }
}

// Concrete creators: mỗi lớp con chỉ viết đúng một dòng tạo object.
class EmailNotifier extends Notifier {
  createSender(): Sender {
    return new EmailSender();
  }
}

class SmsNotifier extends Notifier {
  createSender(): Sender {
    return new SmsSender();
  }
}

class PushNotifier extends Notifier {
  createSender(): Sender {
    return new PushSender();
  }
}

// Biến thể đơn giản hơn: một hàm factory chọn lớp theo tên kênh, không cần lớp con.
const SENDERS: Record<string, new () => Sender> = { email: EmailSender, sms: SmsSender, push: PushSender };

function senderFor(channel: string): Sender {
  return new SENDERS[channel]();
}

const user: User = { email: "lan@example.com", phone: "0901234567", device: "app-7f3a" };
const text = "Đơn DH-2041 đã giao thành công. Cảm ơn bạn!";
for (const notifier of [new EmailNotifier(), new SmsNotifier(), new PushNotifier()]) {
  console.log(notifier.notify(user, text));
}
console.log(`Hàm factory với "sms" → ${senderFor("sms").constructor.name}`);

SmsNotifier tạo SmsSender → 0901234567: Don DH-2041 da giao thanh cong. Cam on ban! (1 tin, phí 500 ₫)

Dòng cuối minh hoạ một biến thể đơn giản hơn mà code thực tế rất hay dùng, đó là hàm factory sender_for tra bảng tên kênh ra lớp cần tạo. Cách này không cần lớp con, nhưng quyết định chọn lớp lại dồn về một chỗ phải biết hết mọi kênh. Factory Method đúng nghĩa thì đặt quyết định ấy vào lớp con, nên lớp cha không cần biết hệ thống có những kênh nào.

Khi nào dùng

  • Bạn có một quy trình chung đã ổn định, và chỉ có một bước trong đó là tạo đối tượng, với loại đối tượng thay đổi theo ngữ cảnh. Kênh thông báo, định dạng file xuất, cổng thanh toán hay kết nối tới từng loại cơ sở dữ liệu đều là những ví dụ quen thuộc.
  • Một framework hay thư viện muốn người dùng tự cắm loại đối tượng của họ vào mà không phải sửa code của framework. Lớp cơ sở của một job hay một controller thường có sẵn các phương thức create_* để bạn ghi đè.
  • Bạn cần thay đối tượng thật bằng bản giả khi test. Lớp con dành cho test chỉ cần ghi đè phương thức tạo là xong.

Khi nào không nên

  • Chỉ có một loại và chưa có dấu hiệu sẽ thêm loại khác. Gọi thẳng constructor là đủ.
  • Không có quy trình chung nào đáng giữ ở lớp cha. Khi đó một hàm factory hay một bảng tra như sender_for gọn hơn nhiều so với cả một cây lớp con.
  • Loại đối tượng được chọn lúc chạy theo cấu hình hay dữ liệu, chứ không theo lớp con nào đang chạy. Truyền đối tượng vào từ bên ngoài, tức dependency injection, thường hợp lý hơn.

Dễ nhầm với

  • Abstract Factory tạo cả một họ đối tượng luôn đi cùng nhau, chẳng hạn bộ gửi, mẫu nội dung và bộ ghi log của cùng một kênh, thông qua một đối tượng factory riêng. Factory Method chỉ là một phương thức tạo một loại đối tượng, nằm ngay trong lớp đang dùng nó.
  • Strategy cũng đổi hành vi bằng cách đổi đối tượng, nhưng đối tượng đó được truyền vào từ bên ngoài và đổi được ngay lúc chạy. Với Factory Method, lớp con tự tạo đối tượng bên trong, và lựa chọn gắn chặt với lớp con.
  • Template Method là họ hàng gần, vì Factory Method thực chất chỉ là một bước của template method, đúng bước tạo đối tượng.
  • Builder lắp một đối tượng phức tạp qua nhiều bước, còn Factory Method trả về một đối tượng hoàn chỉnh chỉ trong một lần gọi.

Ghi chú khi triển khai

  • Factory method nên trả về interface Sender chứ không phải một lớp cụ thể. Nếu lớp cha phải kiểm tra isinstance trên kết quả, interface của bạn đang thiếu một thứ gì đó.
  • Lớp cha có thể cho create_sender() một cài đặt mặc định thay vì để trừu tượng, và lớp con nào cần mới ghi đè.
  • Hãy đặt tên phương thức theo thứ nó tạo ra, như create_sender hay make_connection, để người đọc lớp con biết ngay mình đang ghi đè điểm nào.
  • Khi số lớp con sinh ra chỉ để chọn một constructor ngày càng nhiều, gộp chúng lại thành một hàm factory dùng bảng tra là một bước đơn giản hoá hợp lý.

Kiểm tra nhanh

Sáu câu hỏi ngắn để xem bạn đã nắm Factory Method tới đâu. Chọn một đáp án, lời giải thích sẽ hiện ngay bên dưới.

  1. Câu 1 Trong ví dụ, phương thức nào là factory method?

    create_sender() là bước tạo đối tượng mà lớp cha khai báo và lớp con ghi đè. notify() là quy trình chung dùng kết quả của nó, còn sender_for() là hàm factory tra bảng, một biến thể không cần lớp con.

  2. Câu 2 Công ty muốn thêm kênh Zalo. Với Factory Method, bạn cần làm gì?

    Kênh mới chỉ cần một product mới và một lớp con tạo ra nó. Quy trình trong notify() của lớp cha không phải sửa, nên các kênh cũ cũng không cần test lại.

  3. Câu 3 Trong ví dụ, kênh SMS gửi nội dung ra sao và mất phí bao nhiêu?

    SmsSender bỏ dấu cho vừa tin nhắn, và nội dung đủ ngắn để nằm trong một tin 160 ký tự, nên phí là 500 ₫. Rút gọn còn 28 ký tự là cách của kênh Push, còn thêm tiêu đề là cách của Email.

  4. Câu 4 Khi nào một hàm factory dùng bảng tra như sender_for hợp lý hơn cả một cây lớp con?

    Nếu lớp cha không có quy trình nào để dùng lại, các lớp con chỉ tồn tại để chọn constructor, và một bảng tra làm việc đó gọn hơn nhiều. Factory Method thật sự đáng dùng khi có một quy trình chung cần giữ nguyên.

  5. Câu 5 Factory Method khác Strategy ở điểm nào?

    Cả hai đều đổi hành vi bằng cách đổi đối tượng. Điểm khác là ai chọn và chọn lúc nào, vì Strategy để bên ngoài truyền vào lúc chạy, còn Factory Method để lớp con quyết định ngay khi viết code.

  6. Câu 6 Lớp cha Notifier phải kiểm tra isinstance trên đối tượng mà create_sender() trả về. Điều đó cho thấy gì?

    Factory method nên trả về interface, và lớp cha chỉ nên dùng những gì interface ấy hứa. Khi phải kiểm tra lớp cụ thể, đó là dấu hiệu nên bổ sung phương thức còn thiếu vào Sender.
