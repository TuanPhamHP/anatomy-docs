Behavioral pattern

Interpreter

Interpreter biến một ngôn ngữ nhỏ, chẳng hạn các điều kiện ưu đãi hay phân quyền, thành một cây đối tượng biết tự đánh giá. Nhờ vậy quy tắc trở thành dữ liệu, có thể lưu lại, hiển thị và thay đổi mà không phải sửa code.

Bài toán

Bộ phận kinh doanh muốn tặng ưu đãi cho khách thoả điều kiện sau, và tháng nào họ cũng muốn chỉnh lại một chút:

hạng == "vàng" HOẶC (tổng_đơn >= 500000 VÀ khu_vực == "HN")

Hôm nay có ba khách cần xét:

KháchHạngTổng đơnKhu vực
Anvàng320.000 ₫HCM
Bìnhbạc650.000 ₫HN
Chibạc720.000 ₫ĐN

Điều ta muốn là quy tắc nằm ngoài code, để người làm kinh doanh tự sửa được, còn hệ thống vẫn đánh giá đúng và an toàn.

Khi chưa có Interpreter

Cách làm quen thuộc nhất là viết thẳng quy tắc thành một hàm với vài câu if:

"""Trước khi có Interpreter: quy tắc ưu đãi viết cứng trong một hàm.

Chạy: python3 before.py
"""

]


def eligible(ctx: dict) -> bool:
    # Mỗi lần bộ phận kinh doanh đổi điều kiện là một lần sửa hàm này, review rồi deploy lại.

// Trước khi có Interpreter: quy tắc ưu đãi viết cứng trong một hàm.
// Chạy: node before.ts

type Context = { "hạng": string; "tổng_đơn": number; "khu_vực": string };

const CUSTOMERS: [string, Context][] = [
  ["An", { "hạng": "vàng", "tổng_đơn": 320000, "khu_vực": "HCM" }],
  ["Bình", { "hạng": "bạc", "tổng_đơn": 650000, "khu_vực": "HN" }],
  ["Chi", { "hạng": "bạc", "tổng_đơn": 720000, "khu_vực": "ĐN" }],
];

function eligible(ctx: Context): boolean {
  // Mỗi lần bộ phận kinh doanh đổi điều kiện là một lần sửa hàm này, review rồi deploy lại.
  // Khu vực khác muốn quy tắc khác thì hàm lại mọc thêm nhánh if.
  if (ctx["hạng"] === "vàng") return true;
  if (ctx["tổng_đơn"] >= 500000) {
    if (ctx["khu_vực"] === "HN") return true;
  }
  return false;
}

const dots = (n: number) => String(n).replace(/\B(?=(\d{3})+(?!\d))/g, ".");

console.log("Quy tắc: nằm trong hàm eligible(), muốn đổi phải sửa code");
for (const [name, ctx] of CUSTOMERS) {
  const verdict = eligible(ctx) ? "được ưu đãi" : "không";
  const line = name.padEnd(6) + ctx["hạng"].padEnd(6) + dots(ctx["tổng_đơn"]).padStart(8) + "  " + ctx["khu_vực"].padEnd(5);
  console.log(`${line}-> ${verdict}`);
}

Kết quả thì đúng:

Quy tắc: nằm trong hàm eligible(), muốn đổi phải sửa code
An    vàng   320.000  HCM  -> được ưu đãi
Bình  bạc    650.000  HN   -> được ưu đãi
Chi   bạc    720.000  ĐN   -> không
  • Mỗi lần đổi quy tắc là một lần deploy. Chỉ cần nâng ngưỡng lên 600.000 ₫ cũng phải sửa code, chờ review rồi phát hành lại.
  • Hàm cứ thế phình ra. Mỗi khu vực, mỗi chương trình khuyến mãi muốn một biến thể riêng, và các nhánh if lồng vào nhau tới mức khó đọc.
  • Không ai ngoài lập trình viên đọc được quy tắc đang chạy. Muốn hiển thị quy tắc cho bộ phận kinh doanh xem, bạn phải viết lại nó bằng lời ở một chỗ khác, và hai bản sớm muộn sẽ lệch nhau.
  • Lối tắt eval còn tệ hơn. Lưu quy tắc thành một chuỗi code rồi đưa vào eval hay new Function nghĩa là ai sửa được chuỗi đó thì chạy được bất kỳ lệnh nào trên server. Đừng bao giờ đánh giá quy tắc do người dùng nhập theo cách này.

Lời giải

Ta coi quy tắc là một câu trong một ngôn ngữ rất nhỏ, và biểu diễn câu đó thành một cây. Mỗi loại nút là một lớp có cùng phương thức evaluate(ctx). Nút lá Var đọc một giá trị của khách, Const trả về hằng số viết trong quy tắc. Các nút Equals và AtLeast so sánh hai nhánh con, còn And và Or ghép kết quả của hai nhánh.

Muốn đánh giá cả quy tắc, ta chỉ gọi evaluate ở gốc, và mỗi nút tự gọi xuống các nút con của mình. Cũng chính cái cây đó in lại được thành câu quy tắc, nên thứ được hiển thị luôn là thứ đang chạy.

interpreter.pypython3 interpreter.py
"""Interpreter: quy tắc ưu đãi là một cây biểu thức, lưu như dữ liệu và tự đánh giá.

Chạy: python3 interpreter.py
"""
from dataclasses import dataclass
from typing import Protocol, Union

Value = Union[str, int]
Context = dict[str, Value]


# Mỗi nút của cây biết tự đánh giá trên một khách hàng, và tự in lại chính nó.
class Expr(Protocol):
    def evaluate(self, ctx: Context) -> Value | bool: ...


# Nút lá: đọc một giá trị của khách, hoặc một hằng số viết sẵn trong quy tắc.
@dataclass(frozen=True)
class Var:
    name: str

    def evaluate(self, ctx: Context) -> Value:
        return ctx[self.name]

    def __str__(self) -> str:
        return self.name


@dataclass(frozen=True)
class Const:
    value: Value

    def evaluate(self, ctx: Context) -> Value:
        return self.value

    def __str__(self) -> str:
        return f'"{self.value}"' if isinstance(self.value, str) else str(self.value)


# Nút so sánh: đánh giá hai nhánh con rồi so với nhau.
@dataclass(frozen=True)
class Equals:
    left: Expr
    right: Expr

    def evaluate(self, ctx: Context) -> bool:
        return self.left.evaluate(ctx) == self.right.evaluate(ctx)

    def __str__(self) -> str:
        return f"{self.left} == {self.right}"


@dataclass(frozen=True)
class AtLeast:
    left: Expr
    right: Expr

    def evaluate(self, ctx: Context) -> bool:
        return self.left.evaluate(ctx) >= self.right.evaluate(ctx)

    def __str__(self) -> str:
        return f"{self.left} >= {self.right}"


# Nút ghép: VÀ cần cả hai nhánh đúng, HOẶC chỉ cần một nhánh.
@dataclass(frozen=True)
class And:
    left: Expr
    right: Expr

    def evaluate(self, ctx: Context) -> bool:
        return bool(self.left.evaluate(ctx)) and bool(self.right.evaluate(ctx))

    def __str__(self) -> str:
        return f"({self.left} VÀ {self.right})"


@dataclass(frozen=True)
class Or:
    left: Expr
    right: Expr

    def evaluate(self, ctx: Context) -> bool:
        return bool(self.left.evaluate(ctx)) or bool(self.right.evaluate(ctx))

    def __str__(self) -> str:
        return f"{self.left} HOẶC {self.right}"


# Quy tắc của bộ phận kinh doanh, dựng thẳng thành cây. Thực tế cây này thường được
# đọc từ JSON lưu trong cơ sở dữ liệu, nên đổi quy tắc không cần sửa code.
RULE = Or(
    Equals(Var("hạng"), Const("vàng")),
    And(AtLeast(Var("tổng_đơn"), Const(500000)), Equals(Var("khu_vực"), Const("HN"))),
)

CUSTOMERS = [
    ("An", {"hạng": "vàng", "tổng_đơn": 320000, "khu_vực": "HCM"}),
    ("Bình", {"hạng": "bạc", "tổng_đơn": 650000, "khu_vực": "HN"}),
    ("Chi", {"hạng": "bạc", "tổng_đơn": 720000, "khu_vực": "ĐN"}),
]


def dots(n: int) -> str:
    return f"{n:,}".replace(",", ".")


print(f"Quy tắc: {RULE}")
for name, ctx in CUSTOMERS:
    verdict = "được ưu đãi" if RULE.evaluate(ctx) else "không"
    print(f"{name:<6}{ctx['hạng']:<6}{dots(ctx['tổng_đơn']):>8}  {ctx['khu_vực']:<5}-> {verdict}")
interpreter.tsnode interpreter.ts
// Interpreter: quy tắc ưu đãi là một cây biểu thức, lưu như dữ liệu và tự đánh giá.
// Chạy: node interpreter.ts   (Node 22.18 trở lên chạy thẳng TypeScript)

type Value = string | number;
type Context = Record<string, Value>;

// Mỗi nút của cây biết tự đánh giá trên một khách hàng, và tự in lại chính nó.
interface Expr {
  evaluate(ctx: Context): Value | boolean;
  toString(): string;
}

// Nút lá: đọc một giá trị của khách, hoặc một hằng số viết sẵn trong quy tắc.
class Var implements Expr {
  readonly name: string;
  constructor(name: string) {
    this.name = name;
  }
  evaluate(ctx: Context): Value {
    return ctx[this.name];
  }
  toString(): string {
    return this.name;
  }
}

class Const implements Expr {
  readonly value: Value;
  constructor(value: Value) {
    this.value = value;
  }
  evaluate(): Value {
    return this.value;
  }
  toString(): string {
    return typeof this.value === "string" ? `"${this.value}"` : String(this.value);
  }
}

// Nút so sánh và nút ghép đều có hai nhánh con.
abstract class Binary implements Expr {
  readonly left: Expr;
  readonly right: Expr;
  constructor(left: Expr, right: Expr) {
    this.left = left;
    this.right = right;
  }
  abstract evaluate(ctx: Context): boolean;
}

class Equals extends Binary {
  evaluate(ctx: Context): boolean {
    return this.left.evaluate(ctx) === this.right.evaluate(ctx);
  }
  toString(): string {
    return `${this.left} == ${this.right}`;
  }
}

class AtLeast extends Binary {
  evaluate(ctx: Context): boolean {
    return (this.left.evaluate(ctx) as number) >= (this.right.evaluate(ctx) as number);
  }
  toString(): string {
    return `${this.left} >= ${this.right}`;
  }
}

// VÀ cần cả hai nhánh đúng, HOẶC chỉ cần một nhánh.
class And extends Binary {
  evaluate(ctx: Context): boolean {
    return Boolean(this.left.evaluate(ctx)) && Boolean(this.right.evaluate(ctx));
  }
  toString(): string {
    return `(${this.left} VÀ ${this.right})`;
  }
}

class Or extends Binary {
  evaluate(ctx: Context): boolean {
    return Boolean(this.left.evaluate(ctx)) || Boolean(this.right.evaluate(ctx));
  }
  toString(): string {
    return `${this.left} HOẶC ${this.right}`;
  }
}

// Quy tắc của bộ phận kinh doanh, dựng thẳng thành cây. Thực tế cây này thường được
// đọc từ JSON lưu trong cơ sở dữ liệu, nên đổi quy tắc không cần sửa code.
const RULE: Expr = new Or(
  new Equals(new Var("hạng"), new Const("vàng")),
  new And(new AtLeast(new Var("tổng_đơn"), new Const(500000)), new Equals(new Var("khu_vực"), new Const("HN"))),
);

const CUSTOMERS: [string, Context][] = [
  ["An", { "hạng": "vàng", "tổng_đơn": 320000, "khu_vực": "HCM" }],
  ["Bình", { "hạng": "bạc", "tổng_đơn": 650000, "khu_vực": "HN" }],
  ["Chi", { "hạng": "bạc", "tổng_đơn": 720000, "khu_vực": "ĐN" }],
];

const dots = (n: number) => String(n).replace(/\B(?=(\d{3})+(?!\d))/g, ".");

console.log(`Quy tắc: ${RULE}`);
for (const [name, ctx] of CUSTOMERS) {
  const verdict = RULE.evaluate(ctx) ? "được ưu đãi" : "không";
  const line = name.padEnd(6) + String(ctx["hạng"]).padEnd(6) + dots(ctx["tổng_đơn"] as number).padStart(8) + "  " + String(ctx["khu_vực"]).padEnd(5);
  console.log(`${line}-> ${verdict}`);
}

Quy tắc: hạng == "vàng" HOẶC (tổng_đơn >= 500000 VÀ khu_vực == "HN")
An    vàng   320.000  HCM  -> được ưu đãi
Bình  bạc    650.000  HN   -> được ưu đãi
Chi   bạc    720.000  ĐN   -> không

Trong thực tế, cây này thường được dựng từ JSON lưu trong cơ sở dữ liệu, hoặc từ chính câu chữ qua một parser nhỏ. Đổi ngưỡng 500.000 ₫ hay thêm một khu vực lúc đó chỉ là sửa dữ liệu, còn các lớp nút không thay đổi.

Khi nào dùng

  • Khi có một ngôn ngữ nhỏ và ổn định cần đánh giá nhiều lần, như điều kiện khuyến mãi, quy tắc phân quyền, bộ lọc tìm kiếm do người dùng tự ghép hay công thức tính phí.
  • Khi quy tắc phải nằm ngoài code, do người không phải lập trình viên chỉnh, và bạn cần đánh giá nó một cách an toàn thay vì chạy code tuỳ ý.
  • Khi cùng một quy tắc còn cần làm việc khác ngoài đánh giá, như in ra thành câu, kiểm tra hợp lệ hay giải thích vì sao khách không đạt. Mỗi việc chỉ là thêm một phương thức trên cây.

Khi nào không nên

  • Khi quy tắc gần như không đổi. Vài câu if rõ ràng trong code dễ đọc và dễ test hơn cả một cây lớp.
  • Khi ngôn ngữ lớn dần, có biến, hàm, độ ưu tiên toán tử và thông báo lỗi tử tế. Lúc đó hãy dùng một bộ sinh parser, một thư viện biểu thức hay một rules engine có sẵn, thay vì tự dựng từng lớp nút.
  • Khi hiệu năng là ưu tiên số một. Duyệt cây cho mỗi lần đánh giá chậm hơn code biên dịch sẵn, nên với khối lượng rất lớn người ta thường dịch cây sang dạng khác trước khi chạy.

Dễ nhầm với

  • Composite là hình dạng mà Interpreter dùng. Cây biểu thức chính là một Composite, trong đó nút ghép chứa các nút con và gọi xuống chúng. Interpreter thêm vào đó một ý nghĩa, mỗi cây là một câu trong một ngôn ngữ và evaluate cho ra giá trị của câu.
  • Strategy chọn một thuật toán có sẵn để chạy. Với Interpreter, chính người viết quy tắc ghép ra "thuật toán" bằng cách lắp các nút lại với nhau.
  • Visitor hay đi cùng Interpreter. Khi số thao tác trên cây tăng lên, như đánh giá, in, kiểm tra và tối ưu, bạn có thể tách từng thao tác ra thành một visitor thay vì nhét tất cả vào các lớp nút.

Ghi chú khi triển khai

  • Giữ các nút bất biến. Một cây không đổi sau khi dựng thì dùng chung được giữa nhiều luồng, và có thể lưu vào cache theo phiên bản của quy tắc.
  • Kiểm tra cây ngay khi nạp. Tên biến lạ, so sánh chuỗi với số hay một nút thiếu nhánh nên bị báo lỗi lúc lưu quy tắc, chứ đừng để tới lúc khách đặt hàng mới lộ ra.
  • Chỉ cho phép đúng những nút bạn định nghĩa. Khi đọc quy tắc từ JSON, hãy ánh xạ từng loại nút sang đúng lớp của nó và từ chối mọi thứ khác. Đó là lý do cách này an toàn còn eval thì không.
  • Nghĩ tới lời giải thích. Người dùng thường hỏi vì sao mình không được ưu đãi. Một phương thức trả về nhánh nào đúng, nhánh nào sai trên cây sẽ trả lời câu đó rất gọn.

Kiểm tra nhanh

Sáu câu hỏi ngắn để xem bạn đã nắm Interpreter tới đâu. Chọn một đáp án, lời giải thích sẽ hiện ngay bên dưới.

  1. Câu 1 Một trang quản trị cho phép nhân viên tự tạo bộ lọc khách hàng bằng cách ghép các điều kiện như “trường, phép so sánh, giá trị” với VÀ và HOẶC. Hệ thống nên đánh giá các bộ lọc này thế nào?

    Cây nút cho phép ghép điều kiện tuỳ ý mà vẫn chỉ chạy đúng những phép bạn đã định nghĩa. eval chạy được mọi lệnh nên rất nguy hiểm, còn viết sẵn mọi tổ hợp thì không bao giờ xong.

  2. Câu 2 Trong ví dụ, lớp nào đóng vai TerminalExpression?

    Nút lá không có nhánh con, ở đây là Var và Const. AtLeast và Or là nút ghép vì chúng đánh giá các nhánh con của mình, còn Expr chỉ là interface chung.

  3. Câu 3 Khách Chi có hạng bạc, đơn 720.000 ₫ và ở ĐN. Vì sao cánh tay tín hiệu trong hình vẫn nằm ngang?

    Đơn 720.000 ₫ đủ ngưỡng nên một ngón của cổng VÀ đã nhấc, nhưng điều kiện khu vực sai nên ngón còn lại vẫn đè bàn xuống. Nhánh trái cũng sai vì hạng bạc, mà cổng HOẶC chỉ cần một nhánh đúng chứ không đòi cả hai.

  4. Câu 4 Khi nào nên dùng một thư viện biểu thức hay một rules engine có sẵn thay vì tự dựng các lớp nút?

    Tự dựng lớp nút hợp với một ngôn ngữ nhỏ và ổn định. Khi ngữ pháp phình ra, tự viết parser và đủ loại nút sẽ tốn công và dễ sai, nên một công cụ có sẵn đáng dùng hơn. Còn chuyện tránh eval thì một Interpreter tự viết đã làm được.

  5. Câu 5 Interpreter liên quan thế nào tới Composite?

    Nút ghép như And chứa các nút con và gọi xuống chúng, đúng kiểu Composite. Điều Interpreter thêm vào là mỗi cây là một câu trong một ngôn ngữ, và evaluate tính ra giá trị của câu đó.

  6. Câu 6 Quy tắc được lưu dưới dạng JSON rồi nạp lên thành cây. Điều gì làm cho cách này an toàn?

    Danh sách nút được phép là ranh giới an toàn, vì dữ liệu chỉ ghép được những phép bạn đã viết. Cho JSON tự chọn lớp hay biến nó thành code là mở lại đúng lỗ hổng của eval, còn chờ tới lúc khách đặt hàng mới thấy lỗi thì đã quá muộn.
